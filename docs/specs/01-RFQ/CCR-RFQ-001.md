# RFQ — 요구·인터뷰

## 1. 배경과 동기

사용자는 AI·개발 분야의 대회와 공모전에 꾸준히 참가한다. 지금은 event-us.kr 검색 화면을 직접 열어 조건을 걸고 눈으로 훑은 뒤, 참가할 만한 것을 노션 `대회목록` DB에 손으로 옮겨 적는다. 노션에는 대회명·링크·시작일·마감일·결과날·상태를 두고, 상태(시작 전 / 진행 중 / 제출 / 완료)는 직접 갱신한다.

이 방식은 두 가지가 걸린다. 찾는 일이 매번 반복되고, 며칠 사이트를 안 보면 마감이 지난 뒤에 대회의 존재를 알게 된다. 사용자는 이 찾기·옮겨적기를 매일 자동으로 도는 프로그램에 넘기고, 자신은 "무엇에 참가할지" 판단만 남기기를 원한다.

처음에는 결과를 노션 DB에 그대로 쌓기로 했으나, 2026-09-29에 **노션 대신 이 프로젝트가 만드는 웹 페이지에 넣기로 바꿨다**([[#Q3]] · [[#Q16]]). 노션 연결 토큰을 만들어 붙이는 준비가 번거롭고, 화면을 직접 두면 목록의 모양과 상태 관리를 원하는 대로 둘 수 있어서다.

처음에는 배치를 GitHub Actions에서 돌리고 페이지를 GitHub Pages에 올렸으나, 2026-10-06에 **GitHub를 빼고 배치와 페이지를 사용자의 노트북에서 돌리기로 바꿨다**([[#Q5]] · [[#Q9]] · [[#Q16]]). 2026-10-04에 사용자가 싱크독을 「내 노트북에서 혼자, 밖으로 새지 않게」 쓰기로 해 이 저장소의 원본이 노트북의 싱크독 서버 저장소로 옮겨졌고, 2026-10-06에 GitHub 저장소를 비공개로 바꾸자 무료 계정이라 GitHub Pages가 함께 내려가서다.

## 3. 요구 사항

#### Q1 매일 자동으로 대회를 찾아 줄 것

"AI나 개발 대회를 많이 나가는데, 이걸 자동으로 일배치 돌아서 크롤링해 주는 프로그램을 만들었으면 한다." 지금은 사람이 사이트에 들어가서 찾는 일을 하루 한 번 자동 실행으로 대체한다.

#### Q2 지금 쓰는 검색 조건이 출발점이되, 그대로 쓰지는 않는다

사용자가 평소 쓰는 조건은 event-us.kr의 다음 검색 URL이다.

```
https://event-us.kr/search?query=ai ax&eventtype=대회/공모전&category=IT/프로그래밍&costmin=무료&order=score&date=모든날&page=1
```

검색어 `ai ax`, 행사유형 `대회/공모전`, 분야 `IT/프로그래밍`, 비용 `무료`.

이 조건을 그대로 자동화하면 사용자가 지금 챙기고 있는 대회를 놓친다. 노션에 등록된 10건을 이 조건으로 검색해 본 결과 3건만 잡혔다. 나머지 중 5건은 **event-us에 분명히 있고 행사유형도 `대회/공모전`이 맞는데도** 분야 값이 `IT/프로그래밍`이 아니라서 걸러졌다.

| 노션에 있는 대회 | event-us 분야 값 |
|---|---|
| 제9회 디테크(D-TECH) 공모전 | 인문/사회 |
| 2026 국립공원 위성 모니터링 AI 챌린지 | 과학기술 |
| 제5회 기아 PBV 아이디어 공모전 | 기타 |
| 2026 제3회 국가지식정보 통합플랫폼 디지털집현전 우수사례 공모전 | 과학기술 |
| 2026 데이터·AI 혁신 챌린지 통합경진대회 | 과학기술 |

따라서 분야로 좁히는 방식은 쓰지 않는다. 넓게 가져온 뒤 관련도로 거른다([[#Q12]]).

#### Q3 결과는 이 프로젝트의 웹 페이지 대회 목록에 자동 등록

"기존에는 사진처럼 내가 관리하고 있었다." 수집 결과를 이 프로젝트가 만드는 웹 페이지의 대회 목록에 쌓는다. 처음에는 이미 쓰고 있던 노션 `대회목록` DB에 넣기로 했으나 2026-09-29에 페이지로 바꿨다. 이미 목록에 있는 대회는 다시 추가하지 않는다. 상태(시작 전 / 진행 중 / 제출 / 완료)는 지금처럼 사용자가 페이지에서 직접 관리하며, 프로그램이 건드리지 않는다. 노션에 손으로 적어 둔 기존 대회는 옮기지 않는다.

#### Q4 수집 소스는 여섯 곳으로 한다

"일단 수집하는 소스(출처)가 되는 부분을 어디서 할지 조사 먼저 하자." 후보 15곳을 조사한 결과를 보고 여섯 곳으로 확정했다.

| 소스 | 성격 | 접근 방식 |
|---|---|---|
| event-us.kr | 행사·대회 종합 플랫폼 | 공개 검색 JSON API |
| DACON | AI·데이터 경진대회 전문 (국내) | 목록 페이지의 서버 렌더링 페이로드 |
| Kaggle | AI·데이터 경진대회 전문 (글로벌) | 공식 API. API 토큰 인증 |
| wevity.com | 공모전 포털 | 정적 HTML 목록 |
| AI팩토리 | AI 경진대회 전문 | 정적 HTML 목록 (서버 렌더링) |
| 콘테스트코리아 | 공모전 포털 | 정적 HTML 목록 |

여섯 곳 모두 헤드리스 브라우저 없이 가져올 수 있다. 이것이 배치 소요 시간과 비용을 누르는 전제가 된다.

##### 선정 기준

세 가지를 봤다. ① 목록이 주기적으로 갱신되는가 — 매일 도는 배치라 새 건이 안 나오면 의미가 없다. ② 자동으로 추출할 수 있는가. ③ 사용자가 실제로 원하는 종류의 대회가 거기 있는가 — 노션에 이미 등록된 10건을 각 소스에서 역으로 찾아 검증했다.

##### AI팩토리와 콘테스트코리아를 정적 추출로 확정한 경위

처음 조사에서는 둘 다 "구조화된 레코드를 못 얻었다"고 적었으나, 다시 확인해 보니 도구를 잘못 쓴 것이었다.

| 소스 | 처음 실패한 이유 | 실제 |
|---|---|---|
| AI팩토리 | Next.js의 RSC flight 페이로드만 뒤졌다 | 서버 렌더링 결과가 평문 HTML로 나온다. 제목·상태(`진행중`)·유형(`경진대회`)·상금·주제가 모두 마크업 안에 있다 |
| 콘테스트코리아 | 본문 목록이 아니라 사이드바 인기글을 잡는 셀렉터를 썼다 | 목록 항목의 제목이 `<a>` 안 평문이다 |

##### AI팩토리는 대회당 한 행으로 넣는다

AI팩토리는 대회 하나를 주제별 과제 여러 건으로 나눠 올린다. 2026-09-17 목록에서 `2026 국립공원 위성 모니터링 AI 챌린지`는 과제 4건(`주제 1: 구상나무 고사 탐지 및 분포 분석` 등)이었고, 접수마감일도 과제마다 9/11 · 9/21 · 10/6 · 10/6으로 달랐다.

과제마다 행을 만들면 대회 하나가 네 행이 된다. 과제명이 대회명과 달라 event-us에 올라온 같은 대회와 같은 대회로 알아보지 못하므로, 같은 대회가 과제 행과 대회 행으로 두 번 들어온다.

사용자는 **대회당 한 행**으로 넣기로 했다. 마감일은 과제 가운데 **가장 늦은 접수마감일**을 쓴다. 사용자가 지금 이 대회를 노션에 한 행, 마감일 10/6으로 적어 둔 방식과 같다. 먼저 닫히는 과제의 마감일은 목록에 보이지 않으므로 상세 링크를 열어 확인한다.

##### Kaggle 접근 경로

내부 엔드포인트는 reCAPTCHA로 막혀 있고 목록 페이지는 SPA라 HTML에 데이터가 없다. 공식 API만 열려 있다. 자격증명 없이 호출하면 401이 돌아오는 것까지 확인했다.

인증은 **새 API 토큰**으로 한다. kaggle.com/settings/api에서 "Generate New Token"으로 무료 발급한다. Kaggle 공식 CLI 문서는 사용자명과 키를 담는 `kaggle.json` 방식을 "Legacy API Credentials"로 분류하고 있어, 새 프로젝트를 그 위에 올리지 않는다.

같은 문서에서 대회 목록이 `category` 값을 돌려주고 그 값에 `gettingStarted`·`playground`가 있는 것을 확인했다. [[#Q12]]의 연습용 대회 제외에 이 값을 쓴다.

#### Q5 일배치는 사용자의 노트북에서 돈다

실행 로그가 남아야 한다. 처음에는 PC가 꺼져 있어도 돌아야 한다고 해 별도 서버나 로컬 cron 대신 GitHub Actions를 썼다. 2026-10-06에 **노트북 cron으로 바꿨다.**

2026-10-04에 이 저장소의 원본이 노트북의 싱크독 서버 저장소로 옮겨졌다(1장). 「노트북이 08:50에 꺼져 있던 날은?」이라는 물음에 사용자는 「아 이건 계속 돌게 하면 안되는 건가?」라고 되물었다. 「PC가 꺼져도 돈다」를 지키려면 GitHub에 남아야 하는데, 노트북이 꺼지면 원본을 가진 싱크독도 꺼지고, GitHub 예약은 실제로 2.5~5.5시간 늦었다. 이 설명을 듣고 사용자는 「노트북 cron」을 골랐다. 그래서 노트북이 꺼져 있는 동안에는 돌지 않는다. 늦게 켜진 날에 언제 도는지는 [[#Q10]]에 적는다.

##### 약관 위험을 알고 유지한다

2026-10-06부터 없다 — GitHub Actions를 쓰지 않으므로 이 위험도 없다. 그 전에는 GitHub 추가 제품 약관의 Actions 조항("저장소에 딸린 소프트웨어 프로젝트의 생산·테스트·배포·게시와 무관한 활동"에 호스팅 러너를 쓰지 말라)에 이 배치가 맞는지 판정할 수 없었고, 사용자가 그 위험을 알고 GitHub Actions를 썼다.

#### Q6 알림은 필요 없다

새 대회를 발견해도 메일이나 메신저로 알리지 않는다. 페이지가 갱신되어 있으면 충분하며, 확인은 사용자가 직접 들어가서 한다.

##### 그날 조치가 필요한 고장만은 실행을 실패로 남긴다

알림이 없으면 사용자는 페이지에 새 대회가 **없는** 날에만 실행 기록([[#Q15]])을 열어 보게 된다. 새 대회가 몇 개라도 들어온 날에는 기록 속 경고를 아무도 보지 않는다.

대부분의 경고는 며칠 늦게 봐도 괜찮다. 그러나 **그날 안에 조치하지 않으면 대회를 영영 잃는 경우**가 있다. 마감이 바로 그날인 대회를 목록에 넣지 못한 경우다. 다음 날이면 마감이 지나 [[#Q11]]에 따라 들어올 수 없다.

사용자는 이런 경고만 **실행 자체를 실패로 남기기로 했다.** 처음에는 GitHub Actions에 실패로 표시되고, GitHub 알림 설정에서 실패한 워크플로 알림을 켜 두면 메일로도 받는 것이었다. 2026-10-06에 실패 알림을 「윈도 알림」으로 바꿨다. 실행이 실패하면 노트북에 윈도 알림이 뜬다. 새 대회를 알리는 것이 아니라 도구가 제 일을 못 했음을 알리는 것이라 이 요구와 부딪히지 않는다. 나머지 경고는 기록에만 남는다.

#### Q7 상태와 지우기는 페이지에서 바꾸고 저장소에 저장한다

페이지에서 대회의 상태(시작 전 / 진행 중 / 제출 / 완료)를 바꾸고, 관심 없는 대회를 지운다(목록에서 감춘다). 이 값은 저장소의 파일에 저장된다. 2026-10-06까지는 그래서 어느 기기에서 열어도 같았고, 그 뒤로 페이지는 노트북에서만 열린다([[#Q16]]). 지운 대회는 배치가 다시 넣지 않는다.

##### 페이지가 저장소에 쓰려면 토큰이 필요하다 — 브라우저에 둔다

2026-10-06부터 없다 — 페이지 토큰을 없앴다. 브라우저는 토큰을 갖지 않고, 노트북의 페이지 서버가 저장소에 쓴다([[#Q16]]). 그 전에는 서버 없는 정적 페이지라, 사용자가 이 저장소의 파일 쓰기 권한만 있는 GitHub 토큰(fine-grained)을 페이지에 붙여 넣어 브라우저에 두었고, 토큰이 새면 저장소 파일을 고칠 수 있다는 위험을 알고 받아들였다.

#### Q8 명세는 싱크독으로 관리한다

"싱크독 MCP를 이용해서 개발할 거다." 설계 산출물은 싱크독 11단계 문서 체계에 넣고, 코드보다 명세를 먼저 확정한다.

#### Q9 저장소는 비공개이고 원본은 노트북에 있다

처음에는 GitHub 계정 `HoyoungParkme` 아래 `competition-crawler` 공개 저장소를 썼다. 2026-10-04에 원본이 노트북의 싱크독 서버 저장소로 옮겨졌고, 2026-10-06에 GitHub 저장소를 비공개로 바꿨다. 이어서 GitHub 저장소를 보관(archive)해 GitHub를 완전히 빼기로 했다. 원본은 노트북의 싱크독 서버 저장소 하나다.

비밀값은 본문에 두지 않는다. 처음에는 저장소 Secrets에 넣었고, 2026-10-06부터는 노트북에만 있는 설정 파일(저장소 밖)에 둔다.

| 시크릿 | 쓰는 곳 |
|---|---|
| OpenAI API 키 | [[#Q12]] 관련도 판별 |
| Kaggle API 토큰 | [[#Q4]] Kaggle 수집 |
| 싱크독 개인 토큰 | 배치가 결과를 원본에 올리고, 페이지 서버가 상태를 원본에 저장한다([[#Q7]] · [[#Q16]]) |

처음에는 페이지가 상태를 저장할 때 쓰는 GitHub 토큰([[#Q7]])을 사용자의 브라우저에 두었다. 2026-10-06에 그 토큰을 없앴다.

#### Q10 배치는 매일 아침 08:50 KST에 시작한다

처음 요청은 "배치는 한국 시간 기준 오전 9시로 가자."였다.

처음에는 GitHub Actions에서 돌았다. GitHub 공식 문서를 확인하니 예약 실행은 워크플로가 몰리는 시간에 지연될 수 있고, 몰리는 시간에 **매 정각**이 포함된다고 적혀 있었다. 문서는 정각이 아닌 시각으로 예약하라고 권했다. 09:00은 정확히 그 정각이다.

사용자와 상의해 **08:50 KST에 시작**하기로 했다. 정각 혼잡을 피하고, 조금 밀려도 9시 무렵에는 결과가 목록에 들어가 있게 하려는 것이었다. 오전 9시에 결과를 보고 싶다는 처음 요청의 목적은 그대로다.

실제로는 2026-10-01~06의 08:50 예약이 11:21~14:26 KST에 돌았다(2.5~5.5시간 지연). 한 번 실행은 53~66초였다. 2026-10-06에 노트북 cron으로 바꾸면서([[#Q5]]) 시각은 08:50 그대로 두었다. 노트북 cron은 그 시각에 바로 돈다. 노트북이 08:50에 꺼져 있거나 잠들어 있던 날은 켜진 뒤 첫 매시 50분에 돈다(23:50까지). 23:50까지 한 번도 돌지 못하면 그날은 실행이 없고, 다음 날 08:50에 평소대로 돈다. 예약 실행은 하루 한 번이다.

#### Q11 마감된 대회는 적재하지 않는다

"마감된 대회는 적재하지 마." 수집 시점에 이미 마감일이 지난 대회는 목록에 넣지 않는다.

이미 목록에 들어간 대회가 마감되는 경우는 프로그램이 지우지 않는다. 페이지가 마감 지난 대회를 접어서 보여 주고, 지우는 것은 사용자 몫이다.

#### Q12 관련 없는 대회는 LLM으로 걸러낸다

분야 필터를 쓰지 않으면([[#Q2]]) 창업 경진대회·사진 공모전·영상제·교육과정처럼 관심 밖의 건이 함께 들어온다. event-us만 봐도 접수마감 전 대회가 2026-09-16 기준 56건인데 그중 창업이 14건으로 가장 많았다.

이것을 LLM으로 판별한다. "LLM으로 판별. OpenAI를 쓸 거야." 대회 하나하나에 대해 AI·데이터·개발 분야 대회인지 판단하고, 아닌 것은 목록에 넣지 않는다. 쓸 모델은 [[#Q14]]에서 정한다.

Kaggle에는 상시 열려 있는 연습용 대회(`Getting Started`·`Playground`)가 섞여 있다. 마감일이 먼 미래로 잡혀 있어 [[#Q11]]의 마감 필터로는 걸러지지 않으므로 이쪽도 함께 제외 대상으로 다룬다.

##### 버린 대회도 기록해 다시 묻지 않는다

관심 없다고 버린 대회가 어디에도 기록되지 않으면, 다음 날 같은 대회가 또 후보로 올라와 다시 판별된다. 마감 전까지 매일 되풀이되므로 같은 대회를 수십 번 묻게 되고 비용도 그만큼 는다.

그래서 **남긴 대회뿐 아니라 버린 대회도 기록**해 두고 다시 묻지 않는다. 판별 기준을 바꾸면 이미 버린 대회는 새 기준으로 다시 보지 않으므로, 기준을 바꿀 때는 버린 기록만 비우는 절차를 함께 둔다.

##### 판별이 통째로 실패한 날은 다음 날로 미룬다

판별 한두 건이 실패하면 그 대회는 버리지 않고 남긴다. 판별이 안 됐다고 대회를 잃지 않기 위해서다.

그러나 API 키가 만료되거나 크레딧이 떨어진 날에는 판별이 **통째로** 실패한다. 그날 같은 규칙을 그대로 쓰면 창업·사진 공모전까지 전부 목록에 쏟아지는데, 배치는 성공으로 끝나 알아채기도 어렵다.

그래서 **판별 실패가 절반을 넘는 날에는 판별하지 못한 대회를 그날 넣지 않고 다음 실행으로 미룬다.** 기록에도 남기지 않으므로 다음 실행에서 다시 판별된다. 그날은 경고를 남긴다.

다만 **마감이 바로 그날인 대회는 미루지 않고 넣는다.** 미루면 다음 날에는 마감이 지나 [[#Q11]]에 따라 들어올 수 없기 때문이다. 판별 한두 건이 실패한 날과 같은 처리다. 관심 밖의 대회가 몇 건 섞일 수 있지만, 마감이 그날인 대회는 수가 적고 놓치는 쪽이 더 나쁘다. 그 밖의 대회는 잃지 않고 하루 늦게 들어온다.

#### Q13 Kaggle 대회명은 영문 원문 그대로 둔다

Kaggle은 대회명이 영문이다. 번역하지 않고 원문 그대로 목록에 넣는다. 대회명이 고유명사에 가까워 옮기면 검색도 안 되고 남과 이야기할 때도 안 통한다.

#### Q14 관련도 판별에는 OpenAI의 싼 모델을 쓴다

"그냥 OpenAI 싼 거 쓰면 될 듯." [[#Q12]]의 판별은 "이것이 AI·개발 분야 대회인가"를 가르는 분류 작업이라 소형 모델로 충분하다. 정확한 모델 이름은 구현 시점에 그때의 최신 목록에서 고르고, 설정값으로 빼서 바꿔 끼울 수 있게 둔다.

#### Q15 실행 기록은 두 곳에 남긴다

알림이 없으므로 실행 기록이 이상을 알아채는 주된 통로다. 그날 조치가 필요한 고장만 실행 실패로 드러난다([[#Q6]]). 실행 로그와 저장소 안의 요약 파일 양쪽에 남긴다. 처음에는 실행 로그가 GitHub Actions 로그였고, 2026-10-06부터는 노트북에 남는 실행 로그다([[#Q5]]).

실행 로그는 보관 기간이 지나면 사라지고 과거와 견주려면 실행을 하나씩 열어야 한다. 저장소에 실행마다 소스 건수를 쌓아 두면 그 비교가 자동으로 된다. 그래서 소스가 오류 없이 0건을 준 날을 "새 대회가 없던 날"이 아니라 "파서가 깨진 날"로 알아챌 수 있다.

##### 0건 경고는 0건이 이어지는 동안 매번 붙인다

**꾸준히 건수를 내던 소스가 0건을 내기 시작하면, 0건이 이어지는 동안 매번** 경고를 붙인다. 바로 앞 실행 하나와만 견주면, 0건이 된 첫날의 기록이 다음 날의 비교 기준이 되어 둘째 날부터 경고가 사라진다. 주력 소스가 멈춘 사실이 첫날 한 줄에만 남고 묻힌다.

"꾸준히"는 0건이 시작되기 직전까지 몇 번 연속으로 건수를 냈는지로 가르고, 그 횟수는 설정값으로 둔다. 원래 드문드문 건수를 내던 소스까지 경고하지 않기 위해서다.

다만 정말로 열린 대회가 없는 시기와 파서가 깨진 것은 건수만으로는 구별되지 않는다. 경고를 보면 그 사이트를 직접 열어 확인한다.

#### Q16 대회 목록 페이지는 노트북에 늘 띄워 둔다

처음에는 GitHub Pages에 올리는 정적 페이지였다. 서버도 데이터베이스도 두지 않고, 배치가 저장소에 커밋한 목록 파일을 읽어 보여 줬다. 저장소가 공개라 페이지도 공개였다. 대회 정보는 원래 공개된 것이고 사용자의 상태 값 말고는 개인 정보가 없어 받아들였다.

2026-10-06에 GitHub 저장소를 비공개로 바꾸자 무료 계정이라 GitHub Pages가 함께 내려갔다. 저장소를 다시 공개로 돌려 페이지를 살리는 길을 묻자 사용자는 「포기하고 ㄱㄱ」라고 했다. 목록 페이지는 「노트북에서 살린다」, 띄우기는 「늘 떠 있게」로 정했다. 그래서 페이지는 노트북의 페이지 서버가 늘 띄워 두고, 노트북에서만 열린다. 데이터베이스는 여전히 두지 않는다. 페이지 서버가 원본의 목록 파일과 상태 파일을 읽어 내주고, 사용자가 바꾼 상태를 원본에 커밋한다. 비용은 들지 않는다.

페이지에서 하는 일은 셋이다. 마감일 차례로 목록을 보고, 대회의 상태를 바꾸고, 관심 없는 대회를 지운다([[#Q7]]). 마감이 지난 대회는 접어 둔다([[#Q11]]).
