# PRD — AI·개발 대회 일배치 수집기

## 1. 목표

#### G1 대회를 찾아 노션에 옮겨적는 손일을 없앤다

#### G2 지금 방식으로는 놓치던 대회까지 걸리게 한다

#### G3 노션에 남는 것이 지금 지원 가능하고 관심 분야인 대회만이 되게 한다

#### G4 사람이 손대지 않아도 매일 돌게 한다

## 2. 비목표

| 비목표 | 이유 |
|---|---|
| 대회 조회용 화면을 따로 만들지 않는다 | 노션 `대회목록` DB가 이미 그 역할을 한다 [[CCR-RFQ-001#Q3]] |
| 새 대회를 메일·메신저로 알리지 않는다 | 노션이 갱신되어 있으면 충분하다 [[CCR-RFQ-001#Q6]] |
| `상태` 컬럼을 프로그램이 바꾸지 않는다 | 참가 여부는 사람의 판단이다 [[CCR-RFQ-001#Q3]] |
| 이미 노션에 있는 행을 고치거나 지우지 않는다 | 마감된 기존 행의 정리는 사용자 몫이다 [[CCR-RFQ-001#Q11]] |
| 대회 상세 본문을 수집하거나 요약하지 않는다 | 링크가 있으면 사용자가 직접 읽는다. 소스마다 상세 페이지를 파면 비용이 급등한다 |
| Kaggle 대회명을 한국어로 옮기지 않는다 | 대회명이 고유명사에 가까워 옮기면 검색도 대화도 안 통한다 [[CCR-RFQ-001#Q13]] |
| 참가 신청·제출을 자동화하지 않는다 | 이 도구의 일은 찾아 주는 데까지다 |
| 대회 하나만을 위한 전용 사이트를 개별로 크롤링하지 않는다 | 목록이 갱신되지 않아 매일 돌 이유가 없다 [[CCR-RFQ-001#Q4]] |
| 과거에 마감된 대회를 아카이브로 쌓지 않는다 | 참가할 수 없는 대회는 판단에 쓸모가 없다 [[CCR-RFQ-001#Q11]] |

## 3. 요구사항

### 3.1 기능

#### R1 여섯 소스에서 대회 목록을 수집한다

근거: [[CCR-RFQ-001#Q4]]

event-us.kr · DACON · Kaggle · wevity · AI팩토리 · 콘테스트코리아에서 현재 열려 있는 대회 목록을 가져온다. 여섯 곳 모두 헤드리스 브라우저 없이 가져올 수 있다.

event-us는 분야(`category`)로 좁히지 않는다. 좁히면 사용자가 지금 챙기고 있는 대회가 걸러진다([[CCR-RFQ-001#Q2]]). 행사유형이 `대회/공모전`인 것을 전부 가져온 뒤 뒤쪽 단계에서 거른다.

- [ ] 여섯 소스 각각에서 목록을 가져온다
- [ ] event-us는 `event_type=대회/공모전`만 걸고 `category`는 걸지 않는다
- [ ] 소스별로 몇 건을 가져왔는지 셀 수 있다
- [ ] 헤드리스 브라우저를 쓰지 않는다

#### R2 소스가 달라도 하나의 형식으로 정규화한다

근거: [[CCR-RFQ-001#Q4]], [[CCR-RFQ-001#Q3]], [[CCR-RFQ-001#Q13]]

소스마다 필드 이름과 날짜 형식이 다르다. 노션에 넣기 전에 공통 형식으로 맞춘다.

반드시 채워야 하는 것은 **대회명·상세링크·출처·원천 ID** 넷이다. 원천 ID는 5장에 정한 값을 쓰고, 소스가 그 값을 주지 않으면 상세 링크를 원천 ID로 쓴다. 넷 중 하나라도 채울 수 없는 레코드는 노션에 넣어도 쓸모가 없거나 다음 날 다시 알아볼 수 없으므로 버린다. 버린 건수는 [[#R8]]의 기록에 남긴다. 파서가 레코드를 내기는 하는데 필수 값을 못 채워 전부 버려지는 고장이 조용히 지나가지 않게 하기 위해서다.

접수시작일과 접수마감일은 알 수 있으면 채우고 모르면 비워 둔다. 마감일을 모르는 대회도 버리지 않기 때문이다([[#R3]]).

날짜는 **접수 기준**이며 **KST로 변환한 뒤 날짜만 취한다**(5장). 노션에 손으로 넣은 5건과 event-us 필드를 대조해 확인한 결과다.

| 노션 컬럼 | event-us 필드 | 대조 결과 |
|---|---|---|
| 시작일 | `register_start_date` | 5건 중 3건 일치 (나머지 2건은 사용자가 달리 적음) |
| 마감일 | `register_due_date` | **5건 전부 일치** |

`close_date`(행사 종료일)를 마감일로 쓰면 어긋난다. `2026 국립공원 위성 모니터링 AI 챌린지`는 `register_due_date`가 10/6, `close_date`가 10/14로 8일 차이가 나고 노션에 적힌 값은 10/6이다.

대회명은 소스가 준 그대로 쓴다. Kaggle의 영문 대회명도 번역하지 않는다.

- [ ] 모든 소스의 결과가 같은 형식으로 나온다
- [ ] 대회명·상세링크·출처·원천 ID가 비어 있지 않다
- [ ] 원천 ID를 주지 않는 소스는 상세 링크를 원천 ID로 쓴다
- [ ] 네 값 가운데 하나라도 채울 수 없는 레코드는 버려지고, 버린 건수가 [[#R8]]의 기록에 남는다
- [ ] 날짜는 KST 기준 날짜로 저장된다
- [ ] event-us의 마감일은 `register_due_date`에서 온다
- [ ] 접수시작일이나 접수마감일을 알 수 없으면 빈 값으로 두고, 그 때문에 적재가 실패하지 않는다
- [ ] Kaggle 대회명이 영문 원문 그대로 남는다

#### R3 마감이 지난 대회는 버린다

근거: [[CCR-RFQ-001#Q11]]

**기준일**(5장)보다 접수마감일이 이른 대회는 노션에 넣지 않는다. 마감일을 알 수 없는 대회는 버리지 않고 남긴다 — 놓치는 쪽이 더 나쁘다.

접수마감일이 기준일과 같은 대회는 남긴다. 그날 안에 지원할 수 있기 때문이다.

- [ ] 접수마감일이 기준일보다 이른 대회는 적재되지 않는다
- [ ] 접수마감일이 기준일인 대회는 적재된다
- [ ] 마감일을 알 수 없는 대회는 적재된다
- [ ] Kaggle의 상시 연습용 대회(`Getting Started`·`Playground`)는 마감일과 무관하게 제외된다

#### R4 관심 분야가 아닌 대회는 걸러낸다

근거: [[CCR-RFQ-001#Q12]], [[CCR-RFQ-001#Q14]]

[[#R1]]에서 넓게 가져오므로 관심 밖의 건이 섞인다. event-us만 봐도 접수마감 전 대회가 2026-09-16 기준 56건인데 그중 창업이 14건으로 가장 많았고, 사진 공모전·영상제·교육과정 모집도 들어 있었다.

이것을 OpenAI의 소형 모델로 한 건씩 판별한다. "이것이 AI·개발 분야 대회인가"를 가르는 분류 작업이라 싼 모델로 충분하다. 모델 이름은 설정값으로 빼서 바꿔 끼울 수 있게 둔다.

잠정 기준은 아래와 같다. 첫 실행 결과를 보고 조정한다.

| | 예 |
|---|---|
| 남긴다 | AI·머신러닝·데이터 분석 경진대회, 해커톤, 소프트웨어·개발 공모전, 데이터 활용 공모전, 알고리즘 대회, AI 주제 논문 경진대회 |
| 버린다 | 창업·IR 경진대회, 사진·영상·디자인·문학 공모전, AI와 무관한 논문 공모, 교육과정·부트캠프 모집, 세미나·컨퍼런스 |

##### 한 번 판별한 대회는 다시 묻지 않는다

남긴 대회는 노션에 행이 생기므로 다음 날 [[#R5]]에서 걸러진다. 그러나 버린 대회는 노션 어디에도 남지 않는다. 따로 기록하지 않으면 다음 날 같은 대회가 또 후보가 되어, 마감 전까지 매일 다시 판별된다.

그래서 **남긴 대회와 버린 대회를 모두 기록**하고, 기록에 있는 대회는 판별하지 않는다.

##### 판별 기준을 바꿀 때

기준을 고치면 이미 버린 대회는 새 기준으로 다시 보지 않게 된다. 그래서 기준을 바꿀 때 **버린 기록만 비울 수** 있어야 한다.

새 기준은 바로 넣지 않고 먼저 미리 본다. 기본 브랜치가 아닌 곳에서 노션에 쓰지 않는 모드([[#R7]])로 돌리되, 버린 기록을 없는 것으로 보고 판별하게 한다. 그러면 기록을 비운 뒤 무엇이 들어올지까지 노션과 기록을 건드리지 않고 볼 수 있다. 결과가 괜찮으면 기준 변경과 버린 기록 비우기를 한 번에 기본 브랜치에 넣는다. 둘을 따로 넣으면, 기록만 먼저 비운 경우 그 사이에 돈 실행이 옛 기준으로 다시 버려 비우기가 무효가 되고, 기준만 먼저 넣은 경우 옛 버림 기록 때문에 새 기준으로 다시 보지 못한다.

##### 판별이 실패했을 때

판별 한두 건이 실패하는 날은 그 대회를 버리지 않고 남긴다. 판별이 안 됐다는 이유로 대회를 잃지 않는다.

그러나 API 키 만료나 크레딧 소진처럼 판별이 **통째로** 실패하는 날에 같은 규칙을 쓰면, 관심 밖의 대회가 한꺼번에 노션에 들어가는데 실행은 성공으로 끝난다. 그래서 그날 판별 대상 중 **실패가 절반을 넘으면**, 판별하지 못한 대회는 적재하지도 기록하지도 않는다. 기록에 없으니 다음 실행에서 다시 판별된다. OpenAI 키가 설정에서 빠진 날도 판별이 통째로 실패한 날로 다룬다.

다만 **접수마감일이 기준일인 대회는 미루지 않고 적재한다.** 미루면 다음 날 마감이 지나 [[#R3]]에서 버려지기 때문이다. 관심 밖의 대회가 몇 건 섞일 수 있지만 놓치는 쪽이 더 나쁘다. 나머지 대회는 잃지 않고 하루 늦게 들어온다.

미루는 날이 여러 날 이어지면 그 사이 마감이 지나 놓칠 수 있다. 그래서 미룬 날에는 경고를 남겨 [[#R8]]의 기록으로 알아챌 수 있게 한다.

응답이 기대한 형식이 아닌 경우 — 모델이 답을 거절했거나 응답이 도중에 잘린 경우 — 도 판별 실패로 본다.

- [ ] 판별 결과가 남긴다/버린다 둘 중 하나로 나온다
- [ ] 판별에 쓴 근거를 Actions 로그에서 확인할 수 있다
- [ ] 남긴 대회와 버린 대회가 모두 기록되고, 기록에 있는 대회는 다시 판별하지 않는다
- [ ] 판별 기준을 바꿀 때 버린 기록만 비울 수 있다
- [ ] 노션과 기록을 바꾸지 않고, 버린 기록이 없다고 보고 새 기준으로 판별한 결과를 미리 볼 수 있다
- [ ] 그날 판별 실패가 절반 이하이면, 실패한 대회는 버리지 않고 적재한다
- [ ] 그날 판별 실패가 절반을 넘으면, 판별하지 못한 대회는 적재하지도 기록하지도 않는다. 단, 접수마감일이 기준일인 대회는 적재한다
- [ ] OpenAI 키가 빠져 있으면 판별이 통째로 실패한 날과 같이 처리된다
- [ ] 판별을 미룬 대회는 다음 실행에서 다시 판별된다
- [ ] 판별을 미룬 날은 경고가 남는다
- [ ] 응답이 거절되거나 잘려 형식에 맞지 않으면 판별 실패로 센다
- [ ] 쓰는 모델을 코드 수정 없이 바꿀 수 있다

#### R5 이미 아는 대회는 다시 넣지 않는다

근거: [[CCR-RFQ-001#Q3]], [[CCR-RFQ-001#Q12]]

배치가 매일 돌고 같은 대회가 여러 소스에 올라오므로 중복이 두 방향으로 생긴다. 하나는 어제 넣은 것을 오늘 또 넣는 것이고, 다른 하나는 같은 대회가 서로 다른 소스에서 각각 들어오는 것이다.

사용자가 손으로 넣어 둔 기존 행과도 겹치면 안 된다. 기존 행은 링크가 전용 사이트를 가리키는 경우가 있어 링크만으로는 판정되지 않는다. `2026 Big Data 활용 대회`는 노션 링크가 `dxchallenge.co.kr`인데 event-us에도 같은 대회가 있다.

노션의 현재 행만 보고 판정하면, 사용자가 관심 없어서 지운 행은 근거가 사라져 다음 날 다시 들어온다. 그래서 노션의 현재 행과 함께 [[#R4]]의 기록도 본다. 노션 현재 행과 같은 대회라서 빠진 대회도 남긴 대회로 기록한다. 그래야 사용자가 손으로 넣어 둔 행을 나중에 지워도 소스의 같은 대회가 되살아나지 않는다.

반대 방향의 실수도 막아야 한다. 기록은 지워지지 않고 쌓이므로, 해마다 같은 이름으로 열리는 대회가 작년 기록과 같은 대회로 판정되면 해마다 조용히 빠진다.

판정 규칙은 5장에 적는다.

- [ ] 같은 대회를 이틀 연속 실행해도 행이 하나만 남는다
- [ ] 여러 소스에 올라온 같은 대회가 행 하나로만 들어간다
- [ ] 사용자가 손으로 넣어 둔 행과 겹치는 대회는 새로 추가되지 않는다
- [ ] 사용자가 노션에서 지운 대회가 다음 실행에서 다시 들어오지 않는다. 손으로 넣었던 행도 같다
- [ ] 해가 다른 같은 이름의 대회는 서로 다른 대회로 다뤄진다. 이름에 연도가 없어도 접수 기간으로 가른다

#### R6 노션 `대회목록` DB에 새 대회를 등록한다

근거: [[CCR-RFQ-001#Q3]], [[CCR-RFQ-001#Q7]], [[CCR-RFQ-001#Q11]]

기존 컬럼에 더해 `출처`와 `수집일`을 추가한다. 두 컬럼이 없으면 배치가 만든다. 기존 행은 건드리지 않아 두 컬럼이 빈 값으로 남는다.

| 노션 컬럼 | 채우는 값 |
|---|---|
| 기타 (title) | 대회명 |
| 링크 | 상세 페이지 주소 |
| 시작일 | 접수 시작일. 모르면 비운다 |
| 마감일 | 접수 마감일. 모르면 비운다 |
| 결과날 | 채우지 않는다. 어느 소스에도 결과 발표일이 없다 |
| 상태 | `시작 전`으로 넣는다. 이후 사용자가 관리한다 |
| 출처 | 어느 소스에서 온 건인지 |
| 수집일 | 기준일(5장). 행을 실제로 만든 시각이 자정을 넘겨도 바꾸지 않는다 |

**한 번 들어간 행은 프로그램이 다시 손대지 않는다.** 소스에서 마감일이 연장되거나 대회명이 바뀌어도 노션의 값은 처음 적재한 그대로 둔다. 갱신을 허용하면 사용자가 손으로 고쳐 둔 값까지 덮어쓰게 되고, 어디까지가 프로그램의 영역인지 흐려진다. 마감 연장은 사용자가 상세 링크를 열어 확인한다.

##### 받아들인 위험 — 이 약속은 권한이 아니라 코드가 지킨다

컬럼을 배치가 만들려면 노션 토큰에 수정 권한이 있어야 한다([[CCR-RFQ-001#Q7]]). 수정 권한이 있으면 그 토큰으로 기존 행을 바꾸거나 지울 수도 있다. 따라서 위의 "다시 손대지 않는다"는 노션이 막아 주는 것이 아니라 배치 코드가 지키는 것이다. 토큰이 새거나 배치에 버그가 들어가면 사용자가 `진행 중`·`제출`로 바꿔 둔 행이 덮이거나 지워질 수 있다. 사용자는 이것을 알고 컬럼 자동 생성을 택했다.

- [ ] `출처`·`수집일` 컬럼이 DB에 존재한다. 없으면 배치가 만든다
- [ ] 새 대회가 위 표대로 채워져 등록된다
- [ ] `수집일`은 기준일이다
- [ ] `상태`는 `시작 전`으로만 설정되고 이후 실행에서 덮어쓰지 않는다
- [ ] 기존 행의 어떤 값도 바뀌지 않는다
- [ ] 소스에서 마감일이 바뀌어도 이미 들어간 행의 `마감일`이 갱신되지 않는다
- [ ] 배치 코드에 기존 행을 수정하거나 지우는 호출이 없다

#### R7 매일 아침 08:50 KST에 자동으로 실행된다

근거: [[CCR-RFQ-001#Q10]], [[CCR-RFQ-001#Q5]]

GitHub Actions 스케줄로 돈다. 손으로도 돌릴 수 있어야 한다.

시작 시각이 정각이 아닌 이유가 있다. GitHub의 예약 실행은 워크플로가 몰리는 시간에 밀릴 수 있고, 매 정각이 그 시간이다. 사용자가 오전 9시에 결과를 보기를 원하므로([[CCR-RFQ-001#Q10]]) 정각을 피해 조금 앞선 08:50에 시작한다. 조금 밀려도 9시 무렵에는 결과가 노션에 들어가 있다.

예약 실행이 정확히 그 시각에 시작된다고는 보장할 수 없다. 이 요구가 약속하는 것은 **무엇으로 예약했는가**까지다. 밀려서 늦게 돌아도 결과가 같다는 것은 [[#N5]]가 맡는다.

수동 실행에는 **노션에 쓰지 않는 모드**가 있다. 수집과 판별은 평소대로 하되 노션과 기록은 읽기만 하고, 무엇이 들어갔을지는 로그에만 남긴다. 판별 기준을 바꾸기 전에 미리 보는 데 쓴다([[#R4]]).

**노션에 쓰는 실행은 기본 브랜치에서만 돈다.** 다른 브랜치에서 쓰는 실행이 돌면 기록이 브랜치마다 갈라진다. 그 브랜치의 기록에만 남은 대회는 기본 브랜치의 실행이 모르므로, 사용자가 지운 행이 되살아나고 이미 버린 대회를 다시 묻게 된다. 다른 브랜치에서는 노션에 쓰지 않는 모드로만 돈다.

- [ ] 매일 08:50 KST에 시작하도록 예약된다
- [ ] 정각으로 예약하지 않는다
- [ ] 저장소에서 수동으로 실행할 수 있다
- [ ] 노션에 쓰지 않고 결과만 확인하는 모드로 돌릴 수 있다. 예약 실행은 이 모드가 아니다
- [ ] 노션에 쓰는 실행은 기본 브랜치에서만 돈다

#### R8 실행 결과를 확인할 수 있다

근거: [[CCR-RFQ-001#Q5]], [[CCR-RFQ-001#Q6]], [[CCR-RFQ-001#Q15]]

새 대회 알림은 보내지 않으므로([[CCR-RFQ-001#Q6]]) 이상을 알아채는 주된 통로가 실행 기록이다. 기록은 **GitHub Actions 로그와 저장소 안의 요약 파일 양쪽**에 남긴다.

둘로 나누는 이유가 있다. Actions 로그는 보관 기간이 지나면 사라지고, 과거와 견주려면 실행을 하나씩 열어야 한다. 저장소에 실행마다 한 줄씩 쌓아 두면 그 비교가 자동으로 된다.

##### 요약 파일에는 실행마다 한 줄

같은 날 여러 번 돌리는 일이 있으므로 줄은 날짜가 아니라 **실행 식별자**로 가른다. 각 줄의 결과는 셋 중 하나다.

| 결과 | 뜻 |
|---|---|
| 성공 | 끝까지 돌았다. 경고가 붙을 수 있다 |
| 실패 | 배치가 실패로 판단하고 스스로 끝냈다. 실패 사유의 종류를 함께 적는다 |
| 중단 | 시간 한도 초과나 취소로 배치가 줄을 남기기 전에 끊겼다 |

실패와 중단도 줄을 남겨야 "오늘 실행이 있었는가, 어떻게 끝났는가"를 요약 파일로 알 수 있다. 예외가 둘 있다.
- **노션에 쓰지 않는 모드의 실행은 줄을 남기지 않는다.** 미리보기가 실제 실행의 기록과 섞이지 않게 하기 위해서다
- **저장소 커밋이 끝내 실패한 실행은 줄이 없다.** 줄을 올리는 것 자체가 실패했기 때문이다. Actions 실행 이력에 실패로 남으므로, 요약 파일의 마지막 줄과 Actions 실행 이력을 함께 보면 가를 수 있다

##### 조용한 고장을 드러내는 경고

기록이 있어야 두 가지 조용한 고장을 잡을 수 있다.
- 소스가 **오류 없이 0건을 주는 날**. 예외가 안 났으니 [[#R9]]의 실패로도 안 잡히고, "새 대회가 없던 날"과 구분이 안 된다
- **판별이나 행 생성이 계속 실패하는 날**. [[#R4]]·[[#R6]]은 개별 실패를 삼키고 진행하므로 실행은 성공으로 끝난다. 실패 건수를 남겨야 드러난다

0건 경고는 **꾸준히 건수를 내던 소스가 0건을 내기 시작하면, 0건이 이어지는 동안 매 실행** 붙인다. "꾸준히"는 0건이 시작되기 바로 앞까지 실패 없는 실행에서 연속으로 몇 번 1건 이상을 냈는지로 가르며, 그 횟수는 설정값(기본 3)이다. 바로 앞 실행 하나와만 견주면 0건이 된 첫날의 줄이 다음 날의 기준이 되어 둘째 날부터 경고가 사라진다. 건수는 [[#R2]]의 정규화를 거친 뒤의 것으로 센다. 파서가 레코드를 내더라도 필수 값을 못 채워 모두 버려지면 수집 건수만으로는 드러나지 않기 때문이다.

정말로 열린 대회가 없는 시기와 파서가 깨진 것은 건수만으로는 구별되지 않는다. 경고를 보면 그 사이트를 직접 열어 확인한다.

| 경고 | 붙는 때 | 실행 결과 |
|---|---|---|
| 소스 0건 | 위 기준 | 성공 |
| 판별 미룸 | [[#R4]]에서 판별 실패가 절반을 넘어 미룬 대회가 있다 | 성공 |
| 행 생성 전면 실패 | 한 건 이상 행 생성을 시도했는데 전부 실패했다 | 성공 |
| 오늘 마감 미적재 | 접수마감일이 기준일인 대회의 행을 만들지 못했다 | **실패** |
| 요약 파일 손상 | 요약 파일에 읽히지 않는 줄이 있다 | 성공 |

**오늘 마감 미적재만 실행을 실패로 올린다**([[CCR-RFQ-001#Q6]]). 다른 경고는 며칠 늦게 봐도 되지만 이것은 그날 안에 다시 돌리지 않으면 대회를 영영 잃는다. 알림이 없어 사용자는 노션에 새 행이 없는 날에만 기록을 열어 보는데, 새 행이 몇 개라도 들어온 날에도 알아채게 하려면 Actions에 실패로 드러나야 한다. 사용자가 GitHub에서 실패한 워크플로 알림을 켜 두면 메일로도 받는다.

##### 공개 저장소라 원문은 남기지 않는다

요약 파일에는 원문 예외 문자열을 넣지 않고 실패의 종류만 넣는다. 오류 메시지에는 요청 주소나 헤더가 섞일 수 있고, 저장소 파일은 공개되며 git 이력에서 지워지지 않는다. 상세한 사유는 Actions 로그에만 남긴다.

- [ ] 소스별 수집 건수, 단계별로 걸러진 건수(정규화에서 버림 · 마감 지남 · 이미 아는 대회 · 관심 밖), 최종 적재 건수가 남는다
- [ ] 실패한 소스와 실패의 종류가 요약 파일에, 원문 사유가 Actions 로그에 남는다
- [ ] 적재된 대회의 이름이 Actions 로그에 남는다
- [ ] 요약 파일에 실행마다 한 줄이 쌓인다. 실패·중단으로 끝난 실행도 포함한다
- [ ] 노션에 쓰지 않는 모드의 실행은 요약 파일에 줄을 남기지 않는다
- [ ] 저장소 커밋이 끝내 실패한 실행은 Actions 실행 이력에 실패로 남는다
- [ ] 각 줄에 실행 식별자, 기준일, 실행 종류(예약·수동), 결과(성공·실패·중단)가 있다
- [ ] 결과가 실패인 줄에는 실패 사유의 종류가 있다
- [ ] 각 줄에 판별 실패 건수, 판별을 미룬 건수, 행 생성 실패 건수가 있다
- [ ] 위 표의 다섯 경고가 각자의 조건에서 남는다
- [ ] 0건 경고는 0건이 이어지는 동안 매 실행 남고, 0건 직전까지 연속으로 건수를 내지 않던 소스에는 붙지 않는다
- [ ] 접수마감일이 기준일인 대회의 행을 만들지 못한 실행은 결과가 실패다
- [ ] 요약 파일에 원문 예외 문자열이 들어가지 않는다

#### R9 소스 하나가 실패해도 나머지는 적재된다

근거: [[CCR-RFQ-001#Q4]]

소스 여섯 중 넷은 페이지 구조에 기대는 방식이다. wevity·AI팩토리·콘테스트코리아는 목록 HTML을, DACON은 서버 렌더링 페이로드의 모양을 읽는다. 상대가 개편하면 깨진다. 하나가 깨졌다고 그날 수집이 통째로 날아가면 안 된다.

설정이 빠진 경우도 같은 원칙을 따른다. Kaggle API 토큰은 Kaggle에만 필요하므로, 그것이 빠졌다고 나머지 다섯 소스까지 멈추면 안 된다. 반면 노션 연결 토큰이나 노션 대상 DB 식별자가 빠지면 이미 아는 대회를 가를 수도, 적재할 수도 없으므로 수집을 시작하지 않는다.

- [ ] 한 소스가 예외를 던져도 나머지 소스의 결과가 노션에 적재된다
- [ ] 실패한 소스가 [[#R8]]의 기록에 남는다
- [ ] Kaggle API 토큰이 빠져 있으면 Kaggle만 실패로 다루고 나머지는 적재된다
- [ ] 노션 연결 토큰이나 노션 대상 DB 식별자가 빠져 있으면 수집을 시작하지 않고 실행이 실패로 끝난다
- [ ] 모든 소스가 실패하면 실행이 실패로 끝난다

### 3.2 비기능

#### N1 운영 비용

유료로 나가는 것은 [[#R4]]의 OpenAI 호출뿐이다. 공개 저장소라 Actions는 분 단위로 과금되지 않고 Kaggle API도 무료다.

OpenAI 비용은 호출 수 × 호출당 토큰 × 모델 단가로 정해진다. 아래 목표는 두 가지 전제 위에 선다. 하나는 [[CCR-RFQ-001#Q14]]대로 **소형 모델**을 쓰는 것이고, 다른 하나는 [[#R4]]대로 **한 번 판별한 대회를 다시 묻지 않는** 것이다. 판별은 [[#R5]]를 거친 뒤에만 하므로, 매일 묻는 것은 처음 본 대회뿐이다. 모델을 상위 모델로 바꾸면 같은 호출량에서도 비용이 수십 배로 뛸 수 있으므로, 모델을 바꿀 때 이 목표를 다시 계산한다. 첫 실행은 후보 전체를 판별하므로 그날만 호출이 몰린다.

두 번째 전제에는 빈틈이 있다. 판별 기준을 바꾸기 전의 미리보기([[#R4]])는 기록을 남기지 않으므로 같은 대회를 한 번 더 묻는다. 행 생성이나 저장소 커밋이 실패한 날의 대회도 기록에 남지 않아 다음 실행에서 다시 판별된다. 이 호출도 실제 사용량에 들어가므로 목표 안에서 센다. 가끔 일어나는 일이라 목표를 넘기지 않는 것으로 보되, 넘기면 미리보기 횟수부터 줄인다.

- [ ] 위 두 전제 아래에서, 미리보기와 다시 판별하는 호출을 포함해 월 운영비가 미화 1달러 미만이다

#### N2 배치 소요 시간

- [ ] 한 번 실행이 10분 이내에 끝난다

#### N3 비밀값 취급

근거: [[CCR-RFQ-001#Q9]]

공개 저장소라 값이 코드나 로그에 섞이면 그대로 노출된다. [[#R8]]의 요약 파일도 저장소에 커밋되므로 같은 조건을 받는다. 한 번 노출된 값은 드러난 것으로 보고 즉시 교체한다.

- [ ] 노션 연결 토큰·노션 대상 DB 식별자·OpenAI 키·Kaggle API 토큰이 GitHub Secrets에만 있다
- [ ] 저장소 파일과 실행 로그 어디에도 값이 나타나지 않는다

#### N4 수집 예의

상대 서버에 부담을 주지 않는다.

- [ ] 요청 사이에 간격을 둔다
- [ ] 식별 가능한 User-Agent를 보낸다
- [ ] 각 사이트의 `robots.txt`를 확인하고 금지된 경로를 요청하지 않는다

#### N5 재실행 안전성

실패한 날 다시 돌리는 일이 생긴다. 예약 실행이 밀려 늦게 도는 날도 있고, 시간 초과나 수동 취소로 잡이 도중에 강제로 끊기는 날도 있다.

실행은 **한 번에 하나씩 차례로** 돈다. 두 실행이 같은 노션과 기록을 동시에 읽으면 같은 대회를 둘 다 넣는다. 앞 실행이 돌고 있으면 뒤 실행은 취소되지 않고 기다렸다가, 앞 실행이 남긴 기록을 보고 시작한다. 예약 실행이 밀린 사이 사용자가 수동으로 돌린 날이 여기 해당한다.

노션에 행을 만드는 것과 그 대회를 기록에 적는 것은 한 묶음으로 할 수 없다. 노션이 행을 만들었다고 응답한 대회는 곧바로 기록에 적어, 잡이 끊겨도 그때까지 넣은 대회는 남게 한다. 행은 생겼는데 응답을 받지 못한 대회는 기록에 없지만, 다음 실행에서 노션 현재 행과 같은 대회로 걸러지므로 중복되지 않는다.

- [ ] 같은 날 여러 번 실행해도 노션 결과가 한 번 실행한 것과 같다
- [ ] 두 실행이 겹쳐 돌지 않는다. 뒤 실행은 앞 실행이 끝난 뒤 그 기록을 보고 시작한다
- [ ] 노션 적재 도중 끊겨도 다음 실행에서 이어서 채워진다
- [ ] 잡이 강제로 끊겨도, 그때까지 노션이 행을 만들었다고 응답한 대회는 기록에 남는다
- [ ] 잡이 강제로 끊긴 실행도 요약 파일에 결과 중단으로 한 줄 남는다

## 4. 성공지표

| 지표 | 목표 | 재는 법 |
|---|---|---|
| 손으로 옮겨적은 대회 수 | 월 0건 | 사용자가 직접 추가한 행 수 |
| 놓치지 않는 정도 | 사용자가 따로 발견한 대회 중 배치가 이미 잡아 둔 비율 90% 이상 | 사용자가 새 대회를 알게 됐을 때 노션에 이미 있는지 확인 |
| 잡음 정도 | 새로 적재된 건 중 관심 없는 건의 비율 20% 이하 | 적재 후 사용자가 지우는 행의 비율 |
| 배치 성공률 | 최근 30회 중 28회 이상 성공 | Actions 실행 이력과 요약 파일 |
| 소요 시간 | 10분 이내 | Actions 실행 시간 |
| 운영비 | 월 1달러 미만 | OpenAI 사용량 |

첫 기준선은 이미 잡혀 있다. 노션에 등록된 10건 중 9건이 event-us 한 곳에서만도 검색된다. 나머지 1건(`2026 한국관광 데이터랩 활용 경진대회`)은 여섯 소스 어디에도 없어 이번 범위로는 잡히지 않는다.

## 5. ID 체계와 날짜 매핑

### 5.1 대회의 식별

대회 하나는 **출처 + 그 출처에서의 원천 ID**로 식별한다. 이것이 [[#R5]]의 첫 번째 중복(어제 넣은 것을 오늘 또 넣는 것)을 막는다.

| 소스 | 원천 ID |
|---|---|
| event-us | 검색 결과의 `id` |
| DACON | 페이로드의 `cpt_id` |
| Kaggle | 대회 목록의 `ref` |
| wevity | 상세 링크의 `ix` 값 |
| AI팩토리 | 목록 페이지에 함께 실려 오는 과제의 `id` |
| 콘테스트코리아 | 상세 링크의 `str_no` 값 |

wevity·AI팩토리·콘테스트코리아의 값은 2026-09-16~17에 받은 목록 페이지에서 확인했다. 소스가 개편해 이 값을 주지 않게 되면 절대 주소로 만든 상세 링크를 원천 ID로 쓴다([[#R2]]).

노션 행에는 원천 ID가 없으므로 노션 행과는 **링크**로 견준다. 링크는 추적용 매개변수(`utm_`으로 시작하는 것, `fbclid`)를 뗀 뒤 견준다. 노션에 손으로 넣은 event-us 링크 5개에는 모두 `utm_` 매개변수가 붙어 있었다. 쿼리 문자열을 통째로 떼면 안 된다. wevity와 콘테스트코리아는 원천 ID가 쿼리 문자열 안에 있다.

### 5.2 두 대회가 같은지 판정하는 법

원천 ID로는 소스가 다른 같은 대회를 알아볼 수 없다. 대회명을 정규화해 견주되, 유사도 하나로 판단하지 않는다. 아래 차례로 보고, 앞 단계에서 결론이 나면 뒤 단계는 보지 않는다. 후보끼리, 후보와 노션 행, 후보와 기록 모두 같은 규칙을 쓴다.

| 단계 | 판정 |
|---|---|
| 1 | 출처와 원천 ID가 같으면 **같은 대회**. 노션 행과는 링크가 같으면 같은 대회. 링크가 없거나 다르면 다음 단계로 간다 |
| 2 | 둘 다 연도나 회차가 적혀 있고 서로 다르면 **다른 대회** |
| 3 | 한쪽의 접수시작일이 다른 쪽의 접수마감일보다 뒤면 **다른 대회**. 두 접수마감일이 180일 넘게 차이 나도 **다른 대회**. 필요한 날짜를 모르면 건너뛴다 |
| 4 | 정규화한 대회명이 완전히 같으면 **같은 대회** |
| 5 | 정규화한 대회명의 유사도가 0.80 이상이면 **같은 대회**. 미만이면 판단하지 않는다 |

정규화는 `모집`·`공고`·`안내` 꼬리말, 대괄호 머리말, `(~9/20)` 같은 괄호 날짜를 떼고, `2026년`을 `2026`으로 맞추고, 공백과 기호를 없애는 것이다.

2단계가 없으면 `2026 한국관광 데이터랩 활용 경진대회`가 `2025 한국관광 데이터랩 활용 경진대회`와 0.94로 묶인다. 정작 올바른 짝인 `2026 데이터·AI 혁신 챌린지 통합경진대회`는 0.82라, 유사도 문턱만으로는 둘을 가를 수 없다.

3단계는 이름에 연도가 없는 연례 대회를 위한 것이다. 작년 기록과 이름이 같아도 올해 접수가 작년 마감 뒤에 시작하면 다른 대회다. 접수시작일을 주지 않는 소스도 있어 두 번째 조건을 둔다. 마감이 연장된 대회는 접수시작일이 그대로라 예전 마감일보다 앞이므로 같은 대회로 남는다.

##### 묶음 규칙

같은 대회는 둘이 아니라 여럿이 한 묶음이 된다. 같은 소스 안에도 중복 공고가 있다. 짝마다 판정해 사슬로 이으면, 서로 다른 해의 두 공고가 연도 없는 공고 하나를 사이에 두고 한 묶음이 될 수 있다. 그래서 **같다는 짝이 하나 이상 있고, 2·3단계에서 다르다고 나온 짝이 하나도 없을 때만** 같은 묶음으로 본다. 5단계에서 문턱에 못 미친 짝은 "다르다"가 아니라 "판단하지 않음"이다. 묶음을 노션 행이나 기록과 견줄 때도 같은 규칙을 쓴다.

##### 검증

2026-09-16에 받은 event-us 대회/공모전 2,160건과 노션 10행으로 이 규칙을 돌렸다.

| 확인한 것 | 결과 |
|---|---|
| 노션 10행이 event-us에서 짝을 찾는가 | 9행이 짝을 찾았다. 5행은 1단계(링크), 4행은 4단계(이름)에서. 나머지 1행은 여섯 소스 밖의 대회다. 3단계가 노션 행을 짝과 잘못 가른 경우는 없었다 |
| 접수마감 전 56건끼리 잘못 묶이는가 | 4쌍이 묶였고 모두 실제로 같은 대회를 가리키는 공고였다. `2026 Big Data 활용 대회` 공고 3건끼리 3쌍, 같은 창업 프로그램의 모집 공고와 설명회 안내가 1쌍 |
| 접수마감 전 56건이 지난 대회 2,089건(쌓일 기록을 흉내 냄)과 같은 대회로 잘못 판정되는가 | 날짜 단계가 없던 4단계 규칙으로는 5건이 빠졌다. 이 규칙으로는 0건이다 |

빠졌던 5건 가운데 `2026년 Big Data 활용 대회 참가자 모집`(접수 9/10~9/18)은 이름에 연도가 없는 작년 공고 `[부산광역시] Big Data 활용 대회`(2025-04-24~05-02)와 유사도 0.85로 묶였고, `2026 AI 창업 경진대회`(9/8~9/30)는 전혀 다른 `2026 국방창업경진대회`(6/15~6/26)와 0.83으로 묶였다. 둘 다 3단계에서 갈린다. event-us는 2,160건 중 15건만 접수시작일이 비어 있어, 180일 조건은 이 자료로는 확인되지 않았다.

### 5.3 날짜

전부 **KST 기준 날짜(시각 없음)** 로 다룬다.

event-us가 주는 값은 `+00:00`이 붙은 **UTC 시각**이다. KST 자정은 UTC로 전날 15:00이므로, KST로 변환하지 않고 날짜만 취하면 UTC 15:00 이후의 시각이 하루 이른 날짜가 된다. `2026 국립공원 위성 모니터링 AI 챌린지`의 `register_start_date`는 `2026-08-04T15:00:00+00:00`이고, KST로 8월 5일이며, 노션에 손으로 적힌 시작일도 8월 5일이다. 시간대 표기가 없는 시각이나 날짜만 있는 값은 KST로 보고 변환하지 않는다.

**기준일**은 실행이 시작한 시각을 KST로 바꾼 날짜 하나다. 마감 판정([[#R3]])·`수집일`([[#R6]])·요약 파일의 날짜([[#R8]])가 모두 이 값이며, 실행 도중 자정을 넘겨도 바꾸지 않는다. 실행을 끝맺는 단계도 같은 시작 시각에서 같은 날짜를 구한다.

배치가 도는 곳의 시계에 기대면 안 된다. 08:50 KST는 UTC로 전날 23:50이라, 시계가 UTC인 곳에서 그 날짜를 그대로 쓰면 기준일이 하루 이르다. 그러면 어제 마감된 대회가 걸러지지 않고 들어오고 `수집일`도 하루 이르게 찍힌다. 실행이 09:00 KST 뒤로 밀린 날에는 두 날짜가 같아져 드러나지 않으므로, 날에 따라 나타났다 사라지는 결함이 된다.

## 6. 미결사항

설계를 바꾸는 물음이 하나 있다.

- [ ] AI팩토리는 대회 하나를 주제별 과제 여러 건으로 올린다. 2026-09-17 목록에서 `2026 국립공원 위성 모니터링 AI 챌린지`는 과제 4건(`주제 1: 구상나무 고사 탐지 및 분포 분석` 등)이고, 접수마감일도 과제마다 다르다(9/11 · 9/21 · 10/6 · 10/6). 과제를 그대로 대회로 쓰면 행이 네 개 생기고, 과제명이 대회명과 달라 노션의 기존 행이나 event-us 공고와 같은 대회로 판정되지 않는다. 과제가 속한 페이지의 이름도 대회명일 때가 있고 주최 기관명일 때가 있다. 과제를 대회 하나로 묶을지, 과제마다 행을 만들지 정해야 한다
