# USECASE (Cockburn)

## 0. 이 문서의 형식

Cockburn 형식을 따른다. 사용자 목표 수준은 한 번에 끝나는 목표 하나를, 하위기능 수준은 그 안에서 되풀이되는 조각을 적는다. 확장 번호 `*a`는 기본 흐름의 어느 단계에서든 일어날 수 있는 일이다.

배치는 주 액터가 사람이 아닌 유스케이스가 중심이고([[#UC-A1]]), 사람이 나오는 것은 대회 목록 페이지에서 결과를 쓰는 쪽([[#UC-A2]] · [[#UC-H1]] · [[#UC-H2]])과 고치는 쪽([[#UC-A3]] · [[#UC-A4]])이다. 페이지는 서버 없는 정적 페이지라, 사람이 바꾸는 값도 저장소 파일에 들어간다.

`대회`는 한 소스에서 온 공고 하나를 말한다. 같은 대회가 여러 소스에 올라온 것은 [[#UC-S4]]에서 하나로 묶인다.

### 0.1 이 문서가 쓰는 말

| 말 | 뜻 |
|---|---|
| 기준일 | 실행이 시작한 시각을 KST로 바꾼 날짜. 앞 실행을 기다린 실행([[#UC-A1]] 1c)이면 기다림이 끝나 시작한 시각이다. 이 시각은 배치가 남기는 값이 아니라 실행에 기록되는 값이라, 배치와 마무리 단계가 각자 같은 시작 시각에서 같은 날짜를 구한다([[CCR-PRD-001]] 5.3). 배치가 1을 마치기 전에 멈춰도 마무리 단계는 이 날짜를 구할 수 있다. 실행 도중 자정을 넘겨도 바꾸지 않는다. 마감 판정·`수집일`·실행 요약의 날짜가 모두 이것이다 |
| 처리 이력 | 판별했거나 이미 아는 대회와 같다고 확인한 대회와 그 결과(남김·버림)의 기록. 대회를 다시 알아볼 수 있도록 출처·원천 ID·링크·대회명·접수시작일·접수마감일을 함께 둔다. 묶음의 구성원을 적을 때, 그 구성원에게 없는 접수 날짜는 묶음 대표의 날짜로 채운다. 같은 대회라 날짜도 같고, 날짜 없는 기록이 다음 해 같은 이름의 대회를 가르지 못하는 일을 줄인다([[#UC-S4]] 5b). [[#UC-S5]]가 버림을, [[#UC-S6]]이 남김을, [[#UC-S4]]가 아는 대회로 빠진 묶음의 구성원을 쓴다. 읽는 것은 [[#UC-S4]]다 |
| 실행 요약 | 실행 한 번에 한 줄. 실행 식별자·기준일·실행 종류·결과·건수·경고와, 그 실행을 올린 뒤 처리 이력에 남은 남김 기록의 수를 담는다. [[#UC-S7]]이 쓰고, 배치가 줄을 남기기 전에 멈춘 실행은 마무리 단계가 중단 줄을 쓴다([[#UC-A1]] \*a2). 남김 기록의 수는 마무리 단계가 올리면서 세어 채운다([[#UC-A1]] 9). [[#UC-S7]]·[[#UC-S4]]·[[#UC-A2]]·[[#UC-A3]]과 마무리 단계가 읽는다 |
| 실행 식별자 | 실행 하나를 가르는 값. 실행 번호와 시도 번호를 함께 담아, 같은 실행을 다시 시도한 것도 따로 가른다. 같은 날 여러 번 돈 실행을 가른다. 마무리 단계는 이것으로 배치가 이 실행의 줄을 남겼는지([[#UC-A1]] \*a2), 앞선 올리기가 이미 들어갔는지([[#UC-A1]] 9) 판단한다 |
| 결과 | 실행 요약 한 줄의 결과 값. **성공**(경고가 붙을 수 있다) · **실패**(배치가 실패로 판단하고 끝냄. 전 소스 실패나 파일 읽기 실패처럼 도중에 멈춘 경우다) · **중단**(배치가 기록을 남기기 전에 멈춤) 셋 중 하나. 성공이 아니면 Actions에도 실패로 드러난다. 관리자가 직접 취소한 실행만 Actions에 취소로 남는다 |
| 마무리 단계 | 배치 다음에 도는 마지막 단계. 배치와 같은 실행 시도 안에 있지만 배치와 따로 돌아, 배치가 정상으로 끝나든 멈추든 돈다. 목록 파일·처리 이력·실행 요약을 기본 브랜치에 커밋한다. 목록에 쓰지 않는 모드에서는 아무것도 하지 않는다 |
| 목록에 쓰지 않는 모드 | 미리보기 모드. 목록 파일과 기록 파일을 읽기만 한다. 기본 브랜치에서는 관리자가 수동 실행에서 고를 때만, 다른 브랜치와 Actions 밖(개발자 PC)에서는 늘 이 모드다([[#UC-A1]] 1b) |
| 목록 파일 | 배치가 넣는 대회 목록. 항목마다 식별자(출처 + 원천 ID)·대회명·링크·접수시작일·접수마감일·출처·수집일·판별 근거를 둔다. 상태는 없다. 배치만 쓰고 [[#UC-S6]]이 더하기만 한다. [[#UC-S4]]와 대회 목록 페이지가 읽는다 |
| 상태 파일 | 페이지가 쓰는 파일. 대회 식별자마다 상태(`시작 전` · `진행 중` · `제출` · `완료`)와 감춤 여부, 바꾼 시각을 둔다. 값이 없는 대회는 `시작 전`이고 감추지 않은 것이다. [[#UC-H1]]이 쓰고 페이지가 읽는다. 배치는 읽지도 쓰지도 않는다 |
| 페이지 토큰 | 페이지가 상태 파일을 저장소에 쓸 때 쓰는 GitHub fine-grained 토큰. 이 저장소의 파일 읽기·쓰기 권한만 있다. 참가자의 브라우저에만 있다([[#UC-H2]]) |

**기본 흐름**

1. 스케줄러가 배치를 깨운다. 배치는 **기본 브랜치의 최신 커밋**을 받아 그 커밋의 코드와 목록 파일·기록 파일로 돈다. 실행이 만들어진 때의 커밋이 아니라 시작하는 때의 최신 커밋이다. 시작한 시각을 KST로 바꿔 기준일을 정한다. 마무리 단계도 같은 시작 시각에서 같은 기준일을 구한다(0.1).
2. 여섯 소스에서 대회 목록을 가져온다([[#UC-S1]]).
3. 소스마다 다른 결과를 하나의 형식으로 맞춘다([[#UC-S2]]).
4. 접수마감이 지난 대회를 버린다([[#UC-S3]]).
5. 목록 파일과 처리 이력에 비추어 이미 아는 대회를 뺀다. 아는 대회로 빠진 묶음의 구성원은 이때 처리 이력 파일에 적힌다([[#UC-S4]] 6).
6. 남은 대회가 관심 분야인지 판별한다. 버린 대회는 이때 처리 이력 파일에 적힌다([[#UC-S5]]).
7. 남긴 대회를 목록 파일에 더하고, 같은 때 처리 이력에 남김으로 적는다([[#UC-S6]]).
8. 실행 요약 파일에 이 실행의 한 줄을 남기고 로그를 남긴다([[#UC-S7]]).
9. 마무리 단계가 기본 브랜치의 최신 상태를 다시 받고, 그 위에 이번 실행이 더한 목록 파일 항목·처리 이력 기록·실행 요약 한 줄을 얹어 **한 커밋으로** 올린다. 실행 요약 줄에는 얹은 뒤의 처리 이력에 남은 남김 기록의 수를 적는다([[#UC-S4]] 2c). 올리는 사이 다른 커밋과 엇갈리면 다시 받아 얹기를 되풀이한다. 다시 받은 최신 상태에 이 실행의 식별자를 가진 줄이 이미 있으면, 앞선 올리기가 응답만 끊기고 실제로는 들어간 것이므로 얹지 않고 끝낸다.
10. 결과대로 끝낸다. 성공이면 성공으로, 실패면(2b · 5a) 실패로 끝나 Actions에 실패로 드러난다.

파일 쓰기는 5·6·7·8이 하고 커밋은 9가 한 번만 한다. 나눠 커밋하면 앞 커밋만 성공한 상태가 생겨 목록 파일·처리 이력·실행 요약이 서로 다른 실행을 가리키게 된다.

목록 파일과 처리 이력을 대회마다 곧바로 반영하고 커밋을 배치 밖의 마무리 단계에 맡기는 것은, 배치가 도중에 멈춰도(\*a) 넣은 데까지는 저장소에 올리기 위해서다. 파일은 한 번에 통째로 바뀌게 써서, 쓰다 멈춰도 반쯤 쓴 파일이 남지 않게 한다.

9에서 파일을 통째로 덮어쓰지 않고 이번 실행의 추가분만 최신 상태 위에 얹는 것은, 그사이 관리자가 올린 처리 이력 수정([[#UC-A4]])을 지우지 않기 위해서다. 두 쪽이 파일 끝에 줄을 붙였을 때 텍스트 병합에 맡기면 충돌로 끝나므로, 병합이 아니라 다시 얹기로 한다. 참가자가 페이지에서 올리는 상태 파일 커밋([[#UC-H1]])은 다른 파일이라 부딪히지 않는다.

첫 실행에서 후보가 수백 건이어도 나누지 않고 한 번에 처리한다. 접수마감 전인 것만 남으므로 물량이 무한정 늘지 않는다. 판별 호출이 몰리는 것도 첫날뿐이다. 다음 날부터는 처리 이력에 없는 새 대회만 묻는다.

**확장**

- **\*a. 어느 단계에서든 배치가 8에 닿지 못하고 멈춘다** (시간 한도 초과 · 수동 취소 · 예상하지 못한 오류)
  - \*a1. 목록 파일과 처리 이력은 반영된 데까지 남아 있다.
  - \*a2. 마무리 단계는 배치와 따로 돌므로 그대로 9를 한다. 배치가 쓴 이번 실행의 실행 요약 추가분에 이 실행의 식별자를 가진 줄이 없으면, 같은 시작 시각에서 기준일을 구해 결과 **중단**의 한 줄을 남긴 뒤 커밋하고, 실행을 실패로 끝내 Actions에 드러낸다. 이 줄에도 남김 기록의 수를 적는다. 관리자가 직접 취소한 실행은 Actions에 실패가 아니라 취소로 남는다. 배치가 1을 마치기 전에 멈춘 실행(최신 커밋을 받다가 실패하거나, 시작 직후 오류·취소·시간 초과로 멈춘 경우)도 같다.
  - \*a3. 목록에 쓰지 않는 모드였으면 마무리 단계는 아무것도 하지 않는다(1b).
  - \*a4. 못 넣은 대회는 다음 실행이 채운다. 다만 접수마감일이 기준일인 대회는 다음 날이면 마감이 지나 [[#UC-S3]]에서 버려진다. 관리자가 그날 안에 다시 돌려야 살릴 수 있다([[#UC-A3]] 6).
  - \*a5. 강제 취소나 실행 환경 유실로 마무리 단계까지 돌지 못하면, 실행 요약에 줄이 남지 않고 목록 파일과 처리 이력의 추가분도 올라가지 않는다. Actions 실행 이력에는 실패나 취소로 남는다. 이번 실행이 판별한 대회는 아무것도 올라가지 않았으므로 다음 실행이 다시 판별한다. 관리자는 [[#UC-A3]] 1a3에서 가른다.
- **1a. 예약 실행이 밀려 늦게 시작한다**
  - 1a1. 그대로 진행한다. 늦게 돌아도 결과는 제시간에 돈 것과 같다([[CCR-PRD-001#N5]]).
  - 1a2. 기준일은 실제로 시작한 시점을 **KST로 변환한 날짜**다. 배치가 도는 곳의 시계에 기대지 않는다. 08:50 KST는 UTC로는 전날 23:50이라, 시계가 UTC인 곳에서 그 시계의 날짜를 그대로 쓰면 기준일이 KST보다 하루 이르다. 그러면 [[#UC-S3]]이 "기준일보다 이른" 마감만 버리므로 **어제 마감된 대회가 걸러지지 않고 들어오고**, `수집일`과 실행 요약의 날짜도 하루 이르게 찍힌다. 실행이 09:00 KST 뒤로 밀린 날에는 두 날짜가 같아져 드러나지 않으므로, 날에 따라 나타났다 사라지는 결함이 된다.
- **1b. 관리자가 목록에 쓰지 않는 모드로 실행한다**
  - 1b1. 2부터 6까지 평소대로 돈다. 목록 파일과 처리 이력은 읽기만 한다. 판별 모델은 실제로 부른다. 무엇이 들어갈지 보려면 판별 결과가 필요하기 때문이다.
  - 1b2. 5·6에서 처리 이력에 아무것도 적지 않는다. 7에서 목록 파일에 더하지 않는다. 8에서 실행 요약에 줄을 붙이지 않는다. 9의 마무리 단계는 아무것도 하지 않는다.
  - 1b3. 무엇이 들어갔을지와 판별 근거는 로그에만 남긴다.
  - 1b4. 판별 결과를 기록하지 않았으므로 다음 실제 실행이 같은 대회를 다시 판별한다. 이 호출도 [[CCR-PRD-001#N1]]의 월 비용에 들어간다. 가끔 하는 일이라 목표 안에 든다고 보되, 넘기면 미리보기 횟수부터 줄인다.
  - 1b5. 예약 실행은 이 모드가 아니다. 기본 브랜치에서는 관리자가 수동 실행에서 명시했을 때만 이 모드다. **기본 브랜치가 아닌 곳에서 도는 실행은 관리자의 선택과 상관없이 늘 이 모드다.** 다른 브랜치에서 목록에 쓰면 그 항목과 기록이 기본 브랜치에 없어, 기본 브랜치의 실행이 같은 대회를 다시 넣고 이미 버린 대회를 다시 묻는다([[CCR-PRD-001#R7]]). 페이지가 읽는 것도 기본 브랜치의 파일이다. Actions 밖(개발자 PC)에서 도는 실행도 늘 이 모드다. 마무리 단계가 없어 쓴 기록이 저장소에 올라가지 않기 때문이다.
  - 1b6. 관리자는 이 모드에서 처리 이력의 **버림 기록을 없는 것으로 보고** 판별하게 할 수 있다. 판별 기준을 바꾸기 전에 그 영향을 미리 보는 데 쓴다([[#UC-A4]]).
  - 1b7. 기본 브랜치가 아닌 곳에서 돌 때 코드는 그 브랜치의 것을 쓰고, 처리 이력과 실행 요약은 기본 브랜치의 최신 판을 읽는다. 브랜치에 남아 있는 오래된 사본을 읽으면 그사이 더한 항목과 남김이 빠져, 이미 목록에 있는 대회가 미리보기에 들어갈 것으로 보인다.
- **1c. 같은 배치의 다른 실행이 이미 돌고 있거나 기다리고 있다**
  - 1c1. 그 실행이 끝날 때까지 기다린 뒤 시작한다. 기다리던 실행은 취소되지 않고 차례로 돈다. 차례는 브랜치와 상관없이 이 배치 전체에 하나다.
  - 1c2. 시작할 때 1에서 기본 브랜치의 최신 커밋을 받으므로 앞 실행이 올린 처리 이력을 본다. 두 실행이 같은 목록 파일과 처리 이력을 동시에 읽고 같은 대회를 둘 다 넣는 일을 막는다.
  - 1c3. 기다리는 동안 관리자가 그 실행을 취소하면 배치도 마무리 단계도 돌지 않으므로 실행 요약에 줄이 남지 않는다. 시작하지 않은 실행이라 남길 결과도 없다([[#UC-A3]] 1a3).
  - 1c4. 기다리는 사이 워크플로 정의가 바뀌었으면, 이 실행은 트리거 때의 정의로 돌면서 1에서 받은 새 코드와 어긋날 수 있다. 그래서 배치를 띄우지 않고 결과 중단으로 끝낸다(\*a2). 새로 수동 실행하면 새 정의로 돈다.
- **1d. 필요한 설정이 빠져 있다** (시크릿 누락 등)
  - 1d1. 배치가 돌기 위해 반드시 있어야 하는 시크릿은 없다. 아는 대회는 저장소 파일로 가르고 적재도 파일에 하기 때문이다. 아래 둘은 그 소스와 판별에만 영향을 준다.
  - 1d2. Kaggle API 토큰만 빠져 있으면 Kaggle에 실패 표시(종류: 설정 누락)를 남기고 나머지 소스로 진행한다. 2a와 같다([[#UC-S1]] 1a). 토큰이 틀려 거절된 날과 같은 결과가 된다.
  - 1d3. OpenAI 키만 빠져 있으면 판별할 묶음을 모두 판별 실패로 보고 6b로 간다([[#UC-S5]] 1b). 키가 만료된 날과 같게 다룬다.
- **2a. 소스 하나가 실패한다**
  - 2a1. 그 소스의 결과를 빈 목록으로 두고 실패 표시를 남긴다.
  - 2a2. 3으로 간다. 나머지 소스의 결과는 평소대로 처리된다. 결과는 성공일 수 있다.
  - 2a3. 그 소스에만 있던 대회 가운데 접수마감일이 기준일인 것은, 배치가 알지 못하므로 드러나지 않고 잃는다. 조용히 0건을 내는 날([[#UC-S7]] 2)도 같다. 받아들인 한계다.
- **2b. 여섯 소스가 모두 실패한다**
  - 2b1. 8로 건너뛰어 결과 **실패**(사유: 전 소스 실패)로 한 줄을 남긴다.
  - 2b2. 9에서 커밋한 뒤 실패로 끝낸다. 네트워크나 설정이 통째로 잘못된 경우라 조용히 넘어가지 않는다.
- **5a. 목록 파일이나 처리 이력이 있는데 읽지 못하거나, 처리 이력의 남김 기록이 줄었다**
  - 5a1. 이미 아는 대회를 가를 근거가 없거나 믿을 수 없으므로 판별도 적재도 하지 않는다([[#UC-S4]] 1b · 2b · 2c).
  - 5a2. 8로 건너뛰어 결과 **실패**(사유: 목록 파일 읽기 실패 · 처리 이력 읽기 실패 · 처리 이력 감소)로 한 줄을 남기고, 9에서 커밋한 뒤 실패로 끝낸다. 목록 파일이 손상된 경우의 복구는 [[#UC-A3]] 2e, 처리 이력은 [[#UC-A3]] 2d, 남김 기록이 줄어든 경우는 [[#UC-A3]] 2i.
- **6a. 판별이 몇 건 실패한다** (그날 판별 대상의 절반 이하)
  - 6a1. 실패한 대회를 남김으로 보고 7로 넘긴다([[#UC-S5]] 2b).
- **6b. 판별이 통째로 실패한다** (그날 판별 대상의 절반 초과)
  - 6b1. 판별하지 못한 대회는 7로 넘기지 않고 처리 이력에도 적지 않는다. 다음 실행이 다시 판별한다. 단, 접수마감일이 기준일인 대회는 미루면 잃으므로 남김으로 넘긴다([[#UC-S5]] 2c).
  - 6b2. 판별에 성공한 대회는 평소대로 처리한다.
  - 6b3. 8에서 **판별 미룸 경고**를 붙인다. 결과는 성공이다. 경고로 드러낸다([[CCR-PRD-001#R8]]).
- **9a. 커밋이 되풀이해도 실패한다**
  - 9a1. 실패로 끝낸다. 이번 실행의 목록 파일 항목·처리 이력 추가분과 실행 요약 한 줄이 저장소에 올라가지 못한다. Actions의 실행 이력과 로그에만 남는다.
  - 9a2. 그래서 저장소의 실행 요약만 보면 이 실행이 없었던 것처럼 보인다. 관리자는 [[#UC-A3]] 1a에서 Actions 실행 이력을 함께 본다.
  - 9a3. 이번 실행이 목록 파일에 더한 항목도 올라가지 않았으므로, 다음 실행이 같은 대회를 다시 판별해 넣는다. 반쪽만 남는 일은 없다. 판별 호출이 한 번 더 들 뿐이다([[CCR-PRD-001#N1]]).
  - 9a4. 원인이 저장소 쓰기 권한 같은 설정이면 매일 되풀이된다. 그동안 9a3이 매일 일어나고 Actions 실행이 매일 실패로 남는다. 관리자가 GitHub 실패 알림을 켜 두었으면 매일 메일이 오고, 켜 두지 않았으면 Actions 실행 이력을 볼 때까지 이어진다.
  - 9a5. 넣지 못한 대회 가운데 접수마감일이 기준일인 것은 다음 날이면 [[#UC-S3]]에서 버려진다. 그날 조치가 필요한 이 고장은 이렇게 Actions 실패로 드러나므로 따로 경고를 두지 않는다([[CCR-RFQ-001#Q6]]). 관리자는 그날 안에 다시 돌린다([[#UC-A3]] 6).

**기본 흐름**

1. 참가자가 페이지를 연다. 페이지가 기본 브랜치의 목록 파일과 상태 파일을 읽는다. 목록은 접수마감일 오름차순이고, 마감일을 모르는 대회는 맨 뒤다. 마감이 지난 대회와 지운 대회는 접혀 있다. 상태 파일에 값이 없는 대회는 `시작 전`으로 보인다.
2. `수집일`이 오늘인 대회를 훑는다. 출처나 상태로 거를 수 있다.
3. 관심이 가는 대회의 링크를 새 창으로 열어 상세를 읽는다.
4. 참가하기로 한 대회의 `상태`를 `진행 중`으로 바꾼다([[#UC-H1]]).
5. 관심 없는 대회를 지운다([[#UC-H1]]).
6. 마감이 지난 대회는 접혀 있다. 펼쳐 보고 필요 없으면 지운다. 배치는 지우지 않는다([[CCR-RFQ-001#Q11]]).

**확장**

- **1a. GitHub에서 실행이 실패했다는 알림이 와 있다**
  - 1a1. 오늘 마감인 대회를 넣지 못했을 수 있다([[#UC-A1]] 9a5). 오늘 대회가 있든 없든 그날 안에 관리자 역할로 [[#UC-A3]]으로 간다. 알림은 관리자가 GitHub에서 실패한 워크플로 알림을 켜 둔 경우에만 온다. 켜 두지 않았으면 Actions의 실행 이력에서만 보인다.
- **1b. 페이지가 파일을 읽지 못한다**
  - 1b1. 저장소나 네트워크 문제다. 페이지가 읽지 못했다고 알린다. 새로 고쳐 본다. 목록 파일이 아직 없으면(첫 실행 전) 빈 목록으로 보인다.
- **2a. 오늘 들어온 대회가 없다**
  - 2a1. 페이지만 봐서는 새 대회가 없던 날인지 배치에 문제가 있던 날인지 모른다. 참가자가 관리자 역할로 실행 요약의 마지막 줄을 본다.
  - 2a2. 마지막 줄이 오늘 날짜이고, 결과가 성공이고, 소스 실패 표시도 경고도 없고, 적재가 0건이면 새 대회가 없던 날이다. 끝.
  - 2a3. 오늘 날짜의 줄이 아직 없으면 예약 실행이 밀려 아직 안 끝났을 수 있다. 조금 뒤 다시 연다([[CCR-SCN-001#S1]]). 들어와 있으면 끝. 시간이 지나도 오늘 날짜의 줄이 붙지 않으면 [[#UC-A3]]으로 가서, [[#UC-A3]] 1a대로 Actions 실행 이력과 함께 가른다.
  - 2a4. 그 밖의 경우는 모두 [[#UC-A3]]으로 간다. 결과가 실패나 중단인 경우, 결과가 성공이어도 소스 실패 표시나 경고가 붙은 경우, 적재가 1건 이상인데 페이지에 오늘 대회가 없는 경우다. 마지막은 페이지가 낡은 파일을 보여 주는 것일 수 있으므로 먼저 새로 고친다. 성공이면서 소스 실패 표시나 소스 0건 경고가 있으면 그 소스에서 새 대회를 놓쳤을 수 있으므로 "새 대회가 없던 날"로 보지 않는다.
- **3a. 마감일이 연장된 대회가 있다**
  - 3a1. 목록의 접수마감일은 처음 적재한 값 그대로다. 배치가 갱신하지 않기로 했으므로([[CCR-PRD-001#R6]]) 참가자가 상세 링크를 열어야 안다. 예전 마감일이 지나면 페이지에서 접힌다.
  - 3a2. 갱신을 허용하면 어디까지가 배치의 영역인지 흐려진다. 그래서 받아들인 한계다.
- **4a. Kaggle 대회라 이름이 영문이다**
  - 4a1. 원문 그대로 보인다([[CCR-RFQ-001#Q13]]). 옮기지 않는다.
- **4b. 페이지에 토큰이 없다**
  - 4b1. 읽기는 그대로 된다. 4·5·6에서 바꾸려 하면 토큰이 필요하다고 알린다. [[#UC-H2]]로 토큰을 넣은 뒤 다시 한다.
- **5a. 지운 대회가 다음 실행에서 다시 들어온다**
  - 5a1. 일어나지 않는다. 지우기는 상태 파일에 감춤을 적는 것이고 목록 파일의 항목은 그대로라, [[#UC-S4]]가 그 항목으로 같은 대회를 알아본다([[#UC-S4]] 3). 처리 이력에도 남김으로 적혀 있다.
  - 5a2. 예외는 셋이다. 처리 이력을 예전 판으로 되돌린 경우([[#UC-A3]] 2d2), 처리 이력과 실행 요약이 함께 사라진 경우([[#UC-S4]] 2a) — 두 경우 모두 같은 묶음으로만 기록된 다른 소스의 공고가 새 항목으로 들어온다 —, 접수 기간이 예전 마감일 뒤로 미뤄진 대회가 예전 공고 없이 들어온 경우([[#UC-S4]] 5c)다. 지운 항목 자체는 상태 파일의 감춤이 남아 있어 여전히 접혀 있다.
- **5b. 같은 대회가 두 항목으로 들어와 있다**
  - 5b1. 제목이 많이 달라(유사도 0.90 미만) [[#UC-S4]]가 같은 대회로 묶지 못한 경우다. 참가자가 하나를 지운다([[#UC-H1]]). 두 항목 모두 목록 파일에 남아 있으므로 지운 쪽은 다시 들어오지 않는다.

**기본 흐름**

1. 관리자가 저장소의 실행 요약 파일을 연다. 실행마다 한 줄이 쌓여 있다. 마지막 줄의 날짜와 결과를 먼저 본다.
2. 결과가 실패나 중단인 줄, 소스 실패 표시나 경고가 붙은 줄을 찾는다. 없으면 소스별 건수 추이를 훑는다.
3. 해당 실행의 Actions 로그를 열어 원문 사유를 확인한다.
4. 목록에 쓰지 않는 모드로 배치를 돌려 무엇이 들어갈지만 본다([[#UC-A1]] 1b).
5. 원인을 고친다.
6. **새 수동 실행**으로 배치를 다시 돌린다([[#UC-A1]]). 실패한 옛 실행을 그대로 다시 실행하지 않는다(6b). 결과가 실패나 중단인 줄이 오늘 날짜면 **그날 안에** 돌린다. 접수마감일이 오늘인 대회는 내일이면 들어오지 못한다.
7. 앞 실행에서 이미 들어간 대회는 [[#UC-S4]]에 걸려 빠지고, 못 넣은 것만 들어간다.

**확장**

- **1a. 마지막 줄이 오늘 날짜가 아니다**
  - 1a1. Actions의 실행 이력에서 오늘 실행을 본다.
  - 1a2. 오늘 실행이 기다리고 있거나 돌고 있으면 예약 실행이 밀린 것이다. 새 실행을 돌리지 않고 끝나기를 기다렸다가 1로 간다. 겹쳐 돌려도 [[#UC-A1]] 1c로 차례를 기다리지만, 같은 일을 두 번 하게 된다.
  - 1a3. 오늘 **목록에 쓰는 실행**이 이미 끝났는데 오늘 날짜의 줄이 없으면, 커밋이 실패했거나([[#UC-A1]] 9a) 강제 취소나 실행 환경 유실로 마무리 단계가 돌지 못한 것이다([[#UC-A1]] \*a5). 3으로 가서 로그를 본다. 끝난 실행이 목록에 쓰지 않는 모드였거나 앞 실행을 기다리는 동안([[#UC-A1]] 1c) 취소됐다면 줄이 없는 것이 정상이다. 1a4로 간다.
  - 1a4. 오늘 목록에 쓰는 실행이 아예 없으면 예약 워크플로가 꺼졌거나 예약 실행이 건너뛰어진 것이다. 이때는 실패 기록도 로그도 없다. 워크플로가 켜져 있는지 보고, 꺼져 있으면 켠다. 켜져 있었다면 예약 실행이 건너뛰어진 것이다. 어느 쪽이든 6으로 가서 새 수동 실행을 돌린다.
- **2a. 소스 0건 경고가 붙어 있다**
  - 2a1. 소스가 오류 없이 빈 결과를 주고 있다. 파서가 깨졌거나, 그 소스에 정말로 열린 대회가 없는 것이다. 건수만으로는 둘을 가를 수 없다.
  - 2a2. 실행 요약에서 그 소스의 수집 건수와 정규화 뒤 건수를 본다. 수집은 됐는데 정규화 뒤 0건이면 파서가 레코드는 내지만 대회명이나 링크를 못 채우는 것이다. 3으로 간다.
  - 2a3. 수집 건수부터 0이면 그 사이트를 직접 열어 본다. 열린 대회가 있으면 마크업이나 응답 구조가 바뀐 것이니 3으로 간다. 없으면 고칠 것이 없다. 그 소스가 다시 건수를 낼 때까지 매 실행 경고가 붙는다([[#UC-S7]] 2). 경고에 적힌, 마지막으로 건수를 낸 기준일로 언제부터인지 안다.
- **2b. 소스 실패 표시가 있다**
  - 2b1. 그 소스의 요청이 실패했다. 실패의 종류(연결·응답 코드·형식·수집 금지·설정 누락)를 보고 3으로 간다. 설정 누락이면 Kaggle API 토큰이 시크릿에 있는지 본다.
- **2c. 판별 미룸 경고가 붙어 있다**
  - 2c1. 판별이 절반 넘게 실패했다. 경고에 적힌 원인을 먼저 본다. 키 누락이면 OpenAI 키를 시크릿에 넣는다([[#UC-A1]] 1d3). 호출 실패면 키 만료, 크레딧·지출 한도 소진, 설정한 모델 이름이 없는 모델을 가리키는지, 그 모델이 추론 끄기(`reasoning.effort: none`)를 받는지를 차례로 보고, 모두 아니면 일시 오류다. 추론 끄기를 받지 않는 모델이면 모든 묶음이 요청 오류로 실패한다([[CCR-API-001]] 2.2). 그날 판별 대상이 1건뿐이면 한 번의 일시 오류로도 붙는다. 3으로 간다.
  - 2c2. 미뤄진 대회는 처리 이력에 없으므로 고친 뒤 다음 실행에서 판별된다. 여러 날 이어지는 동안 마감일을 아는 대회는 마감일 당일에 판별 없이 들어오고([[#UC-S5]] 2c1), 마감일을 모르는 대회는 계속 미뤄진다.
- **2d. 결과가 실패이고 실패 사유가 처리 이력 읽기 실패다**
  - 2d1. 처리 이력 파일이 손상됐다. 손으로 고치다 형식을 깬 경우라면 되돌리지 말고 형식만 고친다([[#UC-A4]] 4d). 6으로 간다.
  - 2d2. 그 밖의 손상이면 저장소 이력에서 마지막으로 읽히던 판으로 되돌린다. 처리 이력과 실행 요약을 같은 판으로 함께 되돌린다. 처리 이력만 되돌리면 남김 기록이 실행 요약에 적힌 수보다 적어져 2i에 걸린다. 그 뒤에 적힌 기록은 사라진다. 그사이 같은 묶음으로만 기록된 공고는 다시 들어오고, 버림으로 적힌 대회는 마감 전이면 다시 판별된다([[CCR-PRD-001#N1]]). 목록 파일도 같은 판으로 함께 되돌린다. 그 뒤 더한 항목이 목록에서 사라지지만 처리 이력에도 없으므로 다음 실행이 다시 넣는다. 6으로 간다.
- **2e. 결과가 실패이고 실패 사유가 목록 파일 읽기 실패다**
  - 2e1. 목록 파일이 손상됐다. 손으로 고치다 형식을 깬 것이면 형식만 고친다. 그 밖의 손상이면 목록 파일·처리 이력·실행 요약을 마지막으로 읽히던 판으로 함께 되돌린다(2d2). 목록 파일만 되돌리면 그 뒤 더한 항목이 처리 이력에는 남김으로 남아 있어 다시 들어오지 않고 목록에서만 사라진다. 6으로 간다.
- **2f. 요약 파일 손상 경고가 붙어 있다**
  - 2f1. 실행 요약 파일에 읽히지 않는 줄이 있다. 저장소 이력에서 그 줄이 생긴 커밋을 찾아 고친다.
- **2h. 결과가 실패이고 실패 사유가 전 소스 실패다**
  - 2h1. 네트워크나 실행 환경이 통째로 잘못된 경우다. 3으로 가서 로그를 본다.
- **2i. 결과가 실패이고 실패 사유가 처리 이력 감소다**
  - 2i1. 처리 이력의 남김 기록이 실행 요약에 마지막으로 적힌 수보다 적다([[#UC-S4]] 2c). 손으로 고치다 남김 줄을 지웠거나 파일을 비운 것이다. 저장소 이력에서 줄어든 커밋을 찾아 지워진 줄을 되살린 뒤 6으로 간다.
  - 2i2. 일부러 예전 판으로 되돌린 것이면 실행 요약도 같은 판으로 함께 되돌린다(2d2). 그러면 적힌 수와 남김 기록이 다시 맞는다.
- **3a. Actions 로그가 보관 기간이 지나 사라졌다**
  - 3a1. 실행 요약 파일은 저장소에 남아 있다. 결과·건수·경고·실패의 종류만으로 어느 소스가 언제부터 멈췄는지는 알 수 있다. 원문 사유는 요약에 넣지 않으므로 알 수 없다.
- **6a. 같은 날 여러 번 돌린다**
  - 6a1. 실행은 차례로 돌고([[#UC-A1]] 1c), 각 실행이 앞 실행의 커밋을 받아 시작한다. 그래서 목록 파일이 한 번 돌린 것과 같다.
- **6b. 옛 실행을 그대로 다시 실행했다**
  - 6b1. 다시 실행한 시도는 시도 번호가 달라 실행 식별자가 새로 생기므로, 기록은 따로 남는다. 코드와 기록 파일도 [[#UC-A1]] 1대로 시작할 때의 최신 커밋에서 받는다.
  - 6b2. 다만 워크플로 정의는 처음 실행된 때의 것을 쓴다. 그사이 워크플로 파일을 고쳤다면 반영되지 않고 새 코드와 어긋날 수 있어, 배치를 띄우지 않고 중단으로 끝난다([[#UC-A1]] 1c4와 같다). 그래서 6은 새 수동 실행으로 한다.

**기본 흐름**

1. 관리자가 판별 기준을 고친 변경을 **기본 브랜치가 아닌 곳**에 올린다. 기본 브랜치에 넣는 순간부터 예약 실행이 새 기준을 쓰므로, 확인 전에는 넣지 않는다.
2. 그곳에서 목록에 쓰지 않는 모드를, 버림 기록을 없는 것으로 보게 해서 돌린다([[#UC-A1]] 1b6). 코드는 그 브랜치의 새 기준이고, 처리 이력은 기본 브랜치의 최신 판이다([[#UC-A1]] 1b7). 예전에 버린 대회가 새 기준으로 어떻게 판별되는지 로그로 본다.
3. 결과가 마음에 들지 않으면 1로 돌아간다.
4. 돌고 있는 실행이 없을 때, 기준 변경과 처리 이력의 **버림 기록 비우기**를 **한 커밋으로** 기본 브랜치에 넣는다. 비우기는 브랜치에 있는 처리 이력 사본이 아니라 **넣기 직전의 기본 브랜치 최신 처리 이력**에 대해 한다. 브랜치를 딴 뒤 매일 실행이 새로 적은 버림은 사본에 없어, 사본에서 비우면 그 기록이 남아 미리보기와 달리 다시 판별되지 않는다. 올린 뒤 처리 이력에 버림이 남지 않았는지, 남김 기록의 수가 비우기 전과 같은지 확인한다. 기다리고 있는 실행은 상관없다. 시작할 때 기본 브랜치의 최신 커밋을 받으므로 새 기준과 비운 처리 이력으로 돈다([[#UC-A1]] 1).
5. 다음 실행이 새 기준으로 판별한다. 기다리지 않으려면 새 수동 실행을 돌린다. 남김이 된 것은 목록에 들어가고, 여전히 버림인 것은 다시 처리 이력에 버림으로 적힌다.

**확장**

- **2a. 미리보기에도 비용이 든다**
  - 2a1. 미리보기는 버린 대회를 실제로 판별하고, 5에서 한 번 더 판별한다. 1로 돌아갈 때마다 더 든다. 이 호출도 [[CCR-PRD-001#N1]]의 월 비용에 들어간다. 가끔 하는 일이라 목표 안에 든다고 보되, 넘기면 미리보기 횟수부터 줄인다.
- **2b. 미리보기와 실제 결과가 다르다**
  - 2b1. 그 사이 소스의 내용이 바뀌었거나, 모델의 답이 흔들렸을 수 있다. 미리보기는 예고이지 보장이 아니다.
- **4a. 버림 기록만이 아니라 처리 이력 전체를 비운다**
  - 4a1. 하지 않는다. 목록 파일에 있는 대회는 그 항목으로 막히지만, 같은 묶음으로만 기록된 다른 소스의 공고가 새 항목으로 들어온다.
- **4b. 실행이 돌고 있는 도중에 넣는다**
  - 4b1. 그 실행은 옛 기준으로 판별하고, 마무리 단계에서 최신 상태 위에 버림 기록을 얹는다([[#UC-A1]] 9). 그러면 비운 뒤에 옛 기준의 버림이 다시 적혀 새 기준으로 판별되지 않는다. 그래서 돌고 있는 실행이 끝난 뒤 넣는다.
- **4c. 비운 뒤 되돌리고 싶다**
  - 4c1. 처리 이력 파일은 저장소에 있으므로 그 커밋을 되돌린다.
- **4d. 손으로 고치다 파일 형식이 깨졌다**
  - 4d1. 다음 실행이 처리 이력을 읽지 못해 판별도 적재도 하지 않고 실패로 끝난다([[#UC-S4]] 2b).
  - 4d2. **되돌리지 말고 형식만 고친다.** 비우기 전의 판으로 되돌리면 버림 기록이 돌아와 새 기준의 코드가 그 대회들을 다시 보지 않는데, 경고도 없어 관리자는 끝난 줄 안다. 이미 되돌렸다면 4부터 다시 한다([[#UC-A3]] 2d1).

**기본 흐름**

1. 소스별 조회 조건을 만든다. event-us는 분야를 걸지 않는다. 행사유형 `대회/공모전`과 사이트 검색이 늘 거는 조건(공개한 글 · 숨기지 않은 글), 접수 중이거나 접수마감일을 모르는 공고만 받는 날짜 조건을 건다. wevity와 콘테스트코리아는 사용자가 고른 분야(wevity 다섯 · 콘테스트코리아 둘)마다 따로 받고, 원천 ID가 같은 공고는 하나로 합친다([[CCR-PRD-001#R1]] · [[CCR-API-001]] 3.1).
2. 그 사이트의 `robots.txt`가 허락하는 경로인지 확인하고, 목록을 요청한다. 식별 가능한 User-Agent를 보낸다. 헤드리스 브라우저는 쓰지 않는다.
3. 여러 쪽에 걸쳐 있으면 다음 쪽을 이어 요청한다. 요청 사이에 간격을 둔다.
4. 원본 레코드 목록과 건수를 돌려준다.

**확장**

- **\*a. 어느 단계에서든 한 소스에 쓴 시간이 정해진 상한에 닿는다**
  - \*a1. 진행 중인 요청과 기다림을 끊고 2a2로 간다. 빈 목록과 실패 표시를 돌려준다.
  - \*a2. 수집이 끝나야 판별과 적재가 시작되므로, 소스 하나가 느리다고 계속 기다리면 나머지 소스의 대회까지 적재되지 못한다([[CCR-PRD-001#R9]]).
- **1a. 필요한 자격증명이 설정에 없다**
  - 1a1. 요청하지 않는다. 빈 목록과 실패 표시(종류: 설정 누락)를 돌려준다. 나머지 소스는 평소대로 돈다([[#UC-A1]] 1d2).
- **2a. 요청이 실패하거나, 응답 코드가 성공이 아니거나, 응답이 예상과 다르다**
  - 2a1. 정해진 횟수만큼 다시 시도한다. 상대가 기다리라고 알려 주면 정해진 상한까지만 그만큼 기다린다. 그보다 오래 기다리라고 하면 다시 시도하지 않고 2a2로 간다.
  - 2a2. 그래도 실패하면 빈 목록과 실패 표시를 돌려준다. 예외를 던지지 않는다([[#UC-A1]] 2a). 실패의 종류는 실행 요약으로, 원문 사유는 로그로 간다.
- **2b. 요청은 성공했는데 결과가 0건이다**
  - 2b1. 빈 목록을 실패 표시 없이 돌려준다. 실패가 아니므로 2a와 다르게 다룬다. 이것이 정상인지 아닌지는 [[#UC-S7]] 2가 판단한다.
- **2c. `robots.txt`가 목록 경로를 막고 있다**
  - 2c1. 요청하지 않는다. 빈 목록과 실패 표시(종류: 수집 금지)를 돌려준다.
- **3a. 쪽이 예상보다 훨씬 많다**
  - 3a1. 정해진 상한에서 멈추고 그 사실을 기록한다. 배치가 [[CCR-PRD-001#N2]]를 넘기지 않게 한다.

**기본 흐름**

1. 소스별 필드를 공통 이름으로 옮긴다. event-us의 접수시작일은 `register_start_date`, 접수마감일은 `register_due_date`에서 온다. 원천 ID는 소스마다 정한 값이다(event-us `id` · DACON `cpt_id` · Kaggle `ref` · wevity `ix` · AI팩토리 합친 과제 `id` 가운데 가장 작은 값(1d) · 콘테스트코리아 `str_no`, [[CCR-PRD-001#R2]]).
2. 시각을 KST로 변환한 뒤 날짜만 남긴다. event-us가 주는 값은 `+00:00`이 붙은 UTC 시각이다. KST 자정은 UTC로 전날 15:00이므로, 변환 없이 UTC 날짜를 그대로 쓰면 UTC 15:00 이후의 시각이 하루 이른 날짜가 된다. `2026 국립공원 위성 모니터링 AI 챌린지`의 `register_start_date`는 `2026-08-04T15:00:00+00:00`이고 KST로 8월 5일이며, 노션에 손으로 적힌 시작일도 8월 5일이다.
3. 상세 링크를 절대 주소로 만든다.
4. 대회명 앞뒤의 공백과 보이지 않는 서식 문자를 뗀다. event-us · 콘테스트코리아는 대회명 앞에 BOM(U+FEFF)을 붙여 주는 일이 있다(2026-09-27). HTML에서 읽은 대회명은 브라우저가 보여 주는 대로 이어진 공백을 하나로 모은다. 그 밖에는 소스가 준 그대로 둔다. Kaggle의 영문 대회명도 옮기지 않는다([[CCR-RFQ-001#Q13]]).
5. 공통 형식 레코드를 돌려준다.

**확장**

- **1a. 접수마감일에 해당하는 필드가 그 소스에 없다**
  - 1a1. 빈 값으로 둔다. [[#UC-S3]]이 이 경우를 버리지 않는다.
- **1b. 대회명이나 상세 링크가 비어 있다**
  - 1b1. 그 레코드를 버린다. 목록에 넣어도 쓸모가 없거나 다시 알아볼 수 없다.
  - 1b2. 버린 건수는 실행 요약의 정규화 탈락 건수에 더하고, 버린 레코드의 출처와 이유는 로그에 남긴다([[#UC-S7]]). 파서가 레코드는 내는데 필수 값을 못 채우는 고장이 조용히 지나가지 않게 하기 위해서다.
- **1c. 소스가 원천 ID를 주지 않는다**
  - 1c1. 3에서 만든 절대 주소 상세 링크를 원천 ID로 쓴다. 원천 ID가 없다는 이유로 레코드를 버리지 않는다. 소스가 개편해 식별자가 사라져도 대회를 잃지 않는다.
- **1d. AI팩토리가 대회 하나를 과제 여러 건으로 준다**
  - 1d1. 같은 대회에 속한 과제를 레코드 하나로 합친다([[CCR-PRD-001#R2]]). 대회명은 연도가 든 페이지 이름, 과제가 하나면 과제명, 과제명의 공통 앞부분, 가장 작은 id 과제의 과제명 차례로 정한다. 목록에 대회 이름이 따로 없어 과제명이나 기관 이름이 될 때도 있다. 접수시작일은 가장 이른 과제의 값이고 접수마감일보다 뒤면 비운다. 접수마감일은 가장 늦은 과제의 값이다.
  - 1d2. 원천 ID는 합친 과제 `id` 가운데 가장 작은 값이다. 과제가 뒤에 추가돼도 바뀌지 않는다. 상세 링크는 늘 원천 ID로 삼은 과제의 상세 주소다. 대회 하나만 보여 주는 페이지가 있어도 그 주소는 목록에 없고, 다음 해 대회가 같은 페이지에 걸리면 여러 대회가 걸린 주소가 된다. 여러 대회가 걸린 주소를 쓰면 목록 항목과 링크가 같아져, 판정 1단계에서 다른 대회까지 같은 대회가 될 수 있다([[#UC-S4]]).
  - 1d3. 페이지 이름과 접수시작일이 같은 과제를 한 대회로 본다([[CCR-API-001#GET/aifactory.space/ko/competition]]). 페이지 이름만으로 묶지 않는 것은, 페이지 이름이 주최 기관명일 때가 있고 한 페이지에 해가 다른 대회가 함께 걸려 있기도 해서다.
  - 1d4. 먼저 닫히는 과제의 마감일은 목록에 보이지 않는다. 받아들인 한계다([[CCR-SCN-001#S3]]).
- **2a. 날짜 형식이 파싱되지 않는다**
  - 2a1. 그 날짜만 빈 값으로 두고 레코드는 살린다.
- **2b. 소스가 시간대 표기 없는 시각이나 날짜만 준다**
  - 2b1. 그 값을 KST로 보고 변환하지 않은 채 날짜만 남긴다. 시간대 표기가 붙은 값만 KST로 변환한다. 표기 없는 `2026-09-30 18:00`을 UTC로 보고 9시간을 더하면 10월 1일이 되어 마감일이 하루 늦어지고, 10월 1일 실행이 이미 마감된 대회를 남긴다.

2. 접수마감일이 **기준일보다 이른** 대회를 버린다. 마감일이 기준일과 같은 대회, 곧 오늘이 마감인 대회는 남긴다. 그날 안에 지원할 수 있기 때문이다.

**확장**

- **2a. 접수마감일이 비어 있다**
  - 2a1. 버리지 않고 남긴다. 놓치는 쪽이 잘못 넣는 쪽보다 나쁘다.
  - 2a2. event-us에서 접수마감일이 없는데 행사 종료일까지 지난 공고는 [[#UC-S1]] 1의 조회 조건에서 이미 빠져 여기 오지 않는다. 지금 열린 대회가 아니기 때문이다([[CCR-PRD-001#R3]]).
- **2b. Kaggle의 상시 연습용 대회다**
  - 2b1. 마감일과 무관하게 버린다. `Getting Started`와 `Playground`는 마감일이 먼 미래로 잡혀 있어 2에서 걸러지지 않는다.

**기본 흐름**

1. 목록 파일의 모든 항목을 읽는다.
2. 처리 이력 파일을 읽는다. 남김과 버림이 모두 들어 있다. 남김 기록의 수가 실행 요약에 마지막으로 적힌 수보다 적지 않은지 본다(2c).
3. 둘을 합쳐 `아는 대회` 집합을 만든다.
   - 목록 파일의 항목은 참가자가 페이지에서 지워도 남아 있으므로, 지운 대회도 아는 대회다([[#UC-A2]] 5a). 처리 이력의 남김은 같은 묶음이라 목록에 들어가지 않은 구성원까지 아는 대회로 만든다.
   - 처리 이력의 버림이 있으므로 예전에 관심 밖이라고 버린 대회를 다시 묻지 않는다([[#UC-S5]]).
4. 후보 대회끼리 먼저 같은 대회를 묶는다. 같은 소스 안에도 중복 공고가 있다. 아래 판정에서 같다고 나온 짝을 강한 것부터 차례로 보며, 두 후보가 속한 묶음을 합친다. 합친 묶음 안의 **모든 짝이 같다고 나와야** 합친다. 판정 2·3단계에서 다르다고 나온 짝은 물론, 5단계에서 문턱에 못 미쳐 판단하지 않은 짝이 하나라도 생기면 합치지 않는다. 짝의 차례는 같다고 나온 단계가 앞선 것(1단계 > 4단계 > 5단계)부터, 같은 단계면 유사도가 높은 것부터, 그것도 같으면 소스 우선순위와 원천 ID 순이다. 묶음마다 대표 한 건을 정한다(4a).
5. 각 묶음을 `아는 대회`와 견준다. 아래 둘 중 하나면 묶음 전체를 아는 대회로 본다.
   - 구성원 가운데 하나라도 아는 대회와 판정 1단계로 같다. 이때는 다른 구성원과 그 아는 대회 사이의 2·3단계를 보지 않는다. 같은 공고가 접수 기간을 바꿔 올라와도, 예전 기록에 남은 옛 날짜 때문에 새 대회가 되지 않게 하기 위해서다.
   - 아는 대회 하나가 구성원 가운데 하나 이상과 같고, 어느 구성원과도 2·3단계에서 다르지 않다. 4와 달리 모든 구성원과 같을 필요는 없고, 문턱에 못 미친 짝은 여기서도 "다르다"가 아니라 판단하지 않은 것이다. 묶음 안의 짝이 이미 모두 같아 구성원 하나와 같으면 나머지와도 대개 같고, 모든 구성원을 요구하면 소스마다 다르게 적은 이름 때문에 목록에 이미 있는 대회와 겹치는 항목이 는다.
6. 아는 대회로 빠진 묶음이 그 아는 대회와 **확실하게** 같다고 나왔으면, 처리 이력에 자기 기록(같은 출처·원천 ID)이 없는 구성원을 처리 이력에 적는다. 결과는 견준 아는 대회를 따른다. 목록 파일 항목이면 남김, 처리 이력 기록이면 그 기록의 결과다. 확실하다는 것은 판정 1단계로 같았거나, 연도나 접수 날짜를 실제로 맞대 보고도 갈리지 않고 같다고 나온 경우다.
   - 적는 이유는, 1단계로 이어 주던 구성원이 소스 목록에서 빠진 날 남은 구성원이 예전 기록의 옛 날짜와 갈려 새 대회가 되는 것을 막기 위해서다.
   - 연도·날짜가 없어 이름만으로 같다고 나온 묶음은 적지 않는다(5b). 적어 두면 그 기록이 다음 날부터 같은 공고와 1단계로 이어져, 날짜를 갖춰 올라온 다른 해의 공고까지 막는다.
7. 어느 것과도 같지 않은 묶음만 돌려준다. 대표와 나머지 구성원을 함께 넘긴다. 대표가 남김이나 버림으로 기록될 때 구성원도 같은 결과로 기록되게 하기 위해서다([[#UC-S5]] 5 · [[#UC-S6]] 4).

두 대회가 같은지는 아래 차례로 판정한다. 앞 단계에서 결론이 나면 뒤 단계는 보지 않는다. 링크로 같다고 나온 경우만 2단계를 더 본다. 후보끼리, 후보와 목록 파일 항목, 후보와 처리 이력 기록 모두 같은 규칙을 쓴다([[CCR-PRD-001#R5]]).

| 단계 | 판정 |
|---|---|
| 1 | 출처와 원천 ID가 같으면 **같은 대회**. **링크가 같아도** 같은 대회로 본다. 소스가 개편해 원천 ID가 링크로 바뀐 경우([[#UC-S2]] 1c)를 잇기 위해서다. 다만 링크가 같아도 2단계에서 다르면 다른 대회다. 한 페이지에 해가 다른 대회가 함께 걸리면 링크가 같아지기 때문이다. 링크는 추적용 매개변수(`utm_`으로 시작하는 것, `fbclid`)를 뗀 뒤 견준다. 쿼리 문자열을 통째로 떼지는 않는다. wevity와 콘테스트코리아는 원천 ID가 쿼리 문자열 안에 있다. 링크가 없거나 다르면 다음 단계로 간다 |
| 2 | 둘 다 연도나 회차가 적혀 있고 서로 다르면 **다른 대회** |
| 3 | 한쪽의 접수시작일이 다른 쪽의 접수마감일보다 뒤면 **다른 대회**. 두 접수마감일이 180일 넘게 차이 나도 **다른 대회**. 필요한 날짜를 모르면 그 조건은 건너뛴다 |
| 4 | 정규화한 대회명이 완전히 같으면 **같은 대회**. 정규화는 `모집`·`공고`·`안내` 꼬리말, 대괄호 머리말, `(~9/20)` 같은 괄호 날짜를 떼고, `2026년`을 `2026`으로 맞추고, 공백과 기호를 없애는 것이다 |
| 5 | 정규화한 대회명의 유사도가 0.90 이상이면 **같은 대회**. 미만이면 판단하지 않는다 |

2단계가 없으면 `2026 한국관광 데이터랩 활용 경진대회`가 `2025 한국관광 데이터랩 활용 경진대회`와 0.94로 묶인다. 정작 올바른 짝인 `2026 데이터·AI 혁신 챌린지 통합경진대회`는 0.82라, 유사도 문턱만으로는 둘을 가를 수 없다. 문턱이 0.90이라 이 올바른 짝도 판단하지 않는다. 이름을 이만큼 다르게 쓴 같은 대회는 따로 들어오고 참가자가 하나를 지운다([[#UC-A2]] 5b). 문턱을 0.90으로 두고 모든 짝을 요구하는 이유와 2026-09-27 실측은 [[CCR-PRD-001]] 5.2에 있다.

3단계가 없으면 이름에 연도나 회차를 적지 않고 해마다 같은 이름으로 열리는 대회가, 작년의 처리 이력 기록과 4단계에서 같은 대회로 판정된다. 처리 이력은 지워지지 않으므로 그 대회는 해마다 조용히 빠진다. 접수시작일을 주지 않는 소스도 있어, 두 접수마감일이 180일 넘게 떨어진 경우도 다른 대회로 본다. 3단계는 마감 연장과도 구별된다. 마감이 연장된 대회는 접수시작일이 그대로라 예전 마감일보다 앞이므로 같은 대회로 남고, 목록의 기존 항목을 갱신하지 않는다는 원칙([[CCR-PRD-001#R6]])대로 새 항목이 생기지 않는다. 접수 기간이 예전 마감일 뒤로 통째로 미뤄진 대회는 3단계에서 예전 기록과 다른 대회가 된다. 같은 공고가 목록에 남아 있으면 5의 첫째 조건으로 막히고, 그런 공고 없이 들어오면 새 항목이 생긴다(5c).

2026-09-16에 받은 event-us 2,160건으로 돌렸을 때, 날짜 단계가 없던 규칙으로는 접수 중인 56건 가운데 5건이 지난 대회와 잘못 묶였고 이 규칙으로는 0건이었다([[CCR-PRD-001#R5]]).

묶음의 대표를 고를 때(4a2) 쓰는 소스 우선순위는 아래와 같다.

| 순위 | 소스 | 이유 |
|---|---|---|
| 1 | DACON | 대회를 직접 여는 플랫폼이라 링크가 곧 참가 페이지다 |
| 2 | Kaggle | 같은 이유. 공식 API라 값도 안정적이다 |
| 3 | AI팩토리 | 같은 이유 |
| 4 | event-us | 주최측이 직접 올린 행사 페이지다. 날짜 필드가 손으로 적어 둔 값과 정확히 맞는 것을 확인했다 |
| 5 | wevity | 공모전 포털이라 2차 정보다. 원본으로 한 번 더 타고 들어가야 할 수 있다 |
| 6 | 콘테스트코리아 | 같은 이유 |

**확장**

- **1a. 목록 파일이 없다**
  - 1a1. 빈 목록으로 본다. 첫 실행이 여기 해당한다. 처리 이력에 남김이 있으면 그 대회는 처리 이력으로 아는 대회다.
- **1b. 목록 파일이 있는데 읽히지 않는다**
  - 1b1. 빈 것으로 보지 않는다. 빈 것으로 보면 목록 전체가 다시 들어온다. 판별도 적재도 하지 않는다([[#UC-A1]] 5a). 복구는 [[#UC-A3]] 2e.
- **2a. 처리 이력 파일이 없다**
  - 2a1. 실행 요약에 남김 기록의 수가 적힌 줄이 없으면 빈 이력으로 본다. 첫 실행이 여기 해당한다.
  - 2a2. 적힌 줄이 있으면 남김 기록의 수를 0으로 보고 2c와 같이 견준다.
  - 2a3. 처리 이력과 실행 요약이 함께 사라지면 견줄 값이 없어 첫 실행처럼 돈다. 버린 대회를 다시 판별하고 같은 묶음으로만 기록된 공고가 새 항목으로 들어온다. 목록 파일의 항목은 그대로라 지운 대회는 되살아나지 않는다. 폴더를 옮기거나 두 파일을 함께 지운 경우다. 받아들인 한계다.
- **2b. 처리 이력 파일이 있는데 읽히지 않는다**
  - 2b1. 빈 이력으로 보지 않는다. 빈 것으로 보면 버린 대회를 모두 다시 판별하고 같은 묶음으로만 기록된 공고가 다시 들어온다. 1b와 같이 판별도 적재도 하지 않는다([[#UC-A1]] 5a). 복구는 [[#UC-A3]] 2d.
- **2c. 처리 이력의 남김 기록이 실행 요약에 마지막으로 적힌 수보다 적다**
  - 2c1. 기록이 지워졌거나 비었다. 그대로 두면 버린 대회를 다시 묻고 같은 묶음으로만 기록된 공고가 다시 들어오는데, 첫 실행과 가를 수 없다. 2b와 같이 판별도 적재도 하지 않는다([[#UC-A1]] 5a). 실패 사유는 처리 이력 감소다. 복구는 [[#UC-A3]] 2i.
  - 2c2. 남김 기록은 판별 기준을 바꿀 때도 비우지 않으므로([[#UC-A4]]) 정상적인 손질로는 줄지 않는다. 버림 기록이 줄어드는 것은 견주지 않는다.
- **4a. 한 묶음에 구성원이 여럿이다**
  - 4a1. 접수 시작일·마감일이 더 채워진 쪽을 대표로 삼는다.
  - 4a2. 그것도 같으면 위 소스 우선순위 표에서 앞선 쪽을 대표로 삼는다.
- **4b. 한 후보가 두 후보와 각각 같다고 나오는데, 그 두 후보끼리는 같다고 나오지 않는다**
  - 4b1. 연도 없는 공고 하나가 서로 다른 해의 두 공고를 잇거나, 이름 틀이 비슷한 두 공모전 사이에 제3의 공고가 끼는 경우다. 4의 차례대로 먼저 본 짝 쪽 묶음에 들어가고, 다른 쪽 후보와는 합쳐지지 않는다.
  - 4b2. 두 칸 이상 떨어져 이어진 경우도 같다. A–B–C–D가 차례로 같아도, A와 C · A와 D · B와 D 가운데 하나라도 같다고 나오지 않으면 네 공고는 한 묶음이 되지 않는다. 2026-09-27 자료에서 사슬로 잇던 예전 규칙은 서로 다른 아이디어 공모전 스무 건을 한 묶음으로 만들었다([[CCR-PRD-001]] 5.2).
- **5b. 연도나 접수 날짜가 짝의 한쪽에 없어 2·3단계로 갈리지 않는다**
  - 5b1. 2단계는 양쪽에 연도나 회차가 있어야 가른다. 3단계는 새 공고의 접수시작일과 예전 기록의 접수마감일이 둘 다 있거나, 두 접수마감일이 180일 넘게 떨어져야 가른다. 그래서 연도로 갈리지 않을 때 아래 가운데 하나면 이름만으로 같은 대회가 되어 빠진다. 올해 다시 열린 대회라도 그렇다.
    - 새 공고에 접수 날짜가 없다.
    - 예전 기록(처리 이력·목록 파일 항목)에 접수마감일이 없다.
    - 새 공고에 접수시작일이 없고 두 접수마감일이 180일 안이다. 한 해에 두 번 여는 대회가 여기 해당한다. wevity는 목록에 마감까지 남은 날수만 보여 주어 접수시작일이 없다.
  - 5b2. 첫째와 셋째는 같은 대회가 날짜를 주는 다른 소스에도 올라와 새 공고와 한 묶음이 되면, 그 공고가 예전 기록을 갈라내 들어온다. 둘째는 묶음의 어느 구성원도 그 기록과 갈리지 않아 이것으로도 살아나지 않고, 기록은 지워지지 않으므로 해마다 빠진다. 다만 처리 이력에 구성원을 적을 때 날짜 없는 구성원은 대표의 날짜로 채우므로(0.1), 둘째는 묶음 전체에 날짜가 없던 기록에서만 생긴다.
  - 5b3. 받아들인 한계다. 첫째를 막으려고 날짜 없는 새 공고를 새 대회로 보면, 이미 마감된 대회의 공고가 포털에 남아 있을 때 날짜가 없어 [[#UC-S3]]도 거르지 못하고 다시 들어온다.
- **5c. 접수 기간이 예전 마감일 뒤로 미뤄진 대회가, 예전 기록과 1단계로 이어지는 공고 없이 들어온다**
  - 5c1. 3단계에서 예전 기록과 다른 대회가 되어 판별·적재로 넘어간다. 목록에 같은 대회의 항목이 하나 더 생긴다. 참가자가 예전 항목을 지웠어도 새 항목은 보인다. 날짜만으로는 새 회차와 가를 수 없어 받아들인 한계다. 예전 공고가 목록에 남아 있으면 5의 첫째 조건으로 막힌다.
- **6a. 목록에 쓰지 않는 모드다**
  - 6a1. 아는 대회로 빠진 묶음의 구성원도 처리 이력에 적지 않는다([[#UC-A1]] 1b).

#### UC-S5 대회가 관심 분야인지 판별한다

| 항목 | 내용 |

| 포함(include) | — |
| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**

1. 묶음의 대표에 대해 대회명, 출처, 소스가 준 부가 정보를 모아 판별 요청을 만든다. 부가 정보는 분야 · 태그 · 키워드 · 주최 · 대상 같은 짧은 낱말이고, AI팩토리는 페이지 이름과 과제명이다([[CCR-API-001#POST/api.openai.com/v1/responses]]).
2. OpenAI의 소형 모델에 묻는다. "이것이 AI·개발 분야 대회인가"를 가르는 분류라 싼 모델로 충분하다. 모델 이름은 설정값이라 코드를 고치지 않고 바꿀 수 있다([[CCR-RFQ-001#Q14]]).
3. 남김·버림과 한 줄 근거를 받는다.
4. 결과와 근거를 로그에 남긴다.
5. 버림으로 판정된 묶음을 곧바로 처리 이력 파일에 버림으로 적는다. 대표와 구성원을 모두 적는다.
6. 남김으로 판정된 묶음을 돌려준다. 이 묶음은 [[#UC-S6]]이 목록 파일에 더하면서 처리 이력에 남김으로 적는다.

| | 예 |
|---|---|
| 남긴다 | AI·머신러닝·데이터 분석 경진대회, 해커톤, 소프트웨어·개발 공모전, 데이터 활용 공모전, 알고리즘 대회, AI 주제 논문 경진대회 |
| 버린다 | 창업·IR 경진대회, 사진·영상·디자인·문학 공모전, AI와 무관한 논문 공모, 교육과정·부트캠프 모집, 세미나·컨퍼런스 |

[[#UC-S4]]가 처리 이력으로 이미 판별한 대회를 빼 주므로 같은 대회를 두 번 묻지 않는다. 버린 대회를 처리 이력에 적지 않으면 마감 전까지 매일 같은 대회를 되물어 [[CCR-PRD-001#N1]]의 비용 전제가 깨진다.

**확장**

- **1a. 판별할 묶음이 하나도 없다**
  - 1a1. 호출하지 않고 빈 목록을 돌려준다.
- **1b. OpenAI 키가 설정에 없다**
  - 1b1. 호출하지 않고 모든 묶음을 판별 실패로 표시한다. 2c로 간다. 키가 만료된 날과 같게 다룬다([[#UC-A1]] 1d3).
- **2a. 호출이 실패하거나, 응답이 거절되거나 도중에 잘려 형식에 맞지 않는다**
  - 2a1. 일시적인 실패(속도 제한 · 서버 오류 · 연결 오류 · 요청 시간 초과 · 충돌)면 다시 시도한다. 키 오류 · 권한 없음 · 지출 한도 · 크레딧 소진 · 모델 없음처럼 다시 물어도 같은 답이 올 실패면 다시 시도하지 않고, 아직 묻지 않은 묶음도 묻지 않고 판별 실패로 표시한다. 요청이 잘못됐다는 답은 그 묶음의 입력 탓일 수 있어 그 묶음만 판별 실패로 두고 나머지는 계속 묻는다. 설정 탓이면(모델이 추론 끄기를 받지 않는 경우 등) 모든 묶음이 같은 답으로 실패해 2c가 된다([[CCR-API-001]] 2.2).
  - 2a2. 그래도 안 되면 그 묶음을 "판별 실패"로 표시한다. 모든 묶음을 물었거나 묻기를 멈춘 뒤 2b나 2c로 간다.
- **2b. 판별 실패가 그날 판별 대상의 절반 이하다**
  - 2b1. 판별 실패한 묶음을 남김으로 보고 돌려준다. 참가자가 페이지에서 보고 지우면 되고, 지운 것은 목록 파일의 항목이 남아 있어 다시 들어오지 않는다([[#UC-S4]] 3).
- **2c. 판별 실패가 그날 판별 대상의 절반을 넘는다**
  - 2c1. 판별 실패한 묶음 가운데 접수마감일이 기준일인 것은 남김으로 보고 돌려준다. 미루면 다음 날 [[#UC-S3]]에서 마감이 지나 버려지기 때문이다.
  - 2c2. 나머지 판별 실패 묶음은 **돌려주지도 처리 이력에 적지도 않는다.** 다음 실행에서 처음 보는 대회로 다시 판별된다.
  - 2c3. 판별에 성공한 묶음은 기본 흐름대로 처리한다.
  - 2c4. 미룬 건수와 원인(키 누락이면 1b, 그 밖은 호출 실패)을 **판별 미룸 경고**로 [[#UC-S7]]에 넘긴다. 실행의 결과는 성공으로 둔다([[#UC-A1]] 6b).
  - 2c5. 여러 날 이어지면, 마감일을 아는 대회는 마감일이 기준일이 되는 날 2c1로 판별 없이 들어오므로 잃지는 않는다. 대신 늦게 들어오고 관심 밖 대회가 섞인다. 마감일을 모르는 대회는 판별이 돌아올 때까지 미뤄지므로, 그 사이 소스에서 내려가면 놓친다. 받아들인 한계다([[CCR-SCN-001#S4]]).
- **5a. 목록에 쓰지 않는 모드다**
  - 5a1. 판별은 평소대로 하되 처리 이력에 아무것도 적지 않는다([[#UC-A1]] 1b).

**기본 흐름**

1. 묶음의 대표마다 항목을 만든다.
2. 목록 파일 끝에 항목을 더한다. 식별자가 이미 있으면 더하지 않는다(2a).
3. 곧바로 그 묶음을 처리 이력에 남김으로 적는다. 대표와 구성원을 모두 적는다.
4. 파일은 한 번에 통째로 바뀌게 쓴다. 모두 넣은 뒤에 한꺼번에 쓰지 않는다. 저장소 커밋은 [[#UC-A1]] 9의 마무리 단계가 한 번에 한다.

| 항목의 값 | 채우는 값 |
|---|---|
| 식별자 | 출처 + 원천 ID([[CCR-PRD-001]] 5.1) |
| 대회명 | 대회명. Kaggle은 영문 원문 그대로 |
| 링크 | 상세 페이지 주소 |
| 접수시작일 | 접수 시작일. 없으면 비워 둔다 |
| 접수마감일 | 접수 마감일. 없으면 비워 둔다 |
| 출처 | 대회가 온 소스 |
| 수집일 | 기준일 |
| 판별 근거 | [[#UC-S5]]가 받은 한 줄 근거. 판별 없이 들어온 대회는 그 사정(판별 실패 · 오늘 마감) |

상태는 목록 파일에 없다. 상태 파일에 값이 없는 대회를 페이지가 `시작 전`으로 보여 준다([[#UC-A2]]). `결과날`은 두지 않는다. 결과 발표일을 주는 소스는 콘테스트코리아뿐이다. 둘지는 [[CCR-PRD-001]] 6장.

**한 번 들어간 항목은 다시 손대지 않는다.** 소스에서 마감일이 바뀌어도 갱신하지 않는다([[CCR-PRD-001#R6]]). 배치는 목록 파일에 더하는 경로만 둔다. 기존 항목을 고치거나 지우는 경로를 두지 않는다. 상태 파일은 읽지도 쓰지도 않는다. 마감이 지난 항목도 지우지 않는다. 페이지가 접는다.

**확장**

- **2a. 식별자가 이미 목록 파일에 있다**
  - 2a1. [[#UC-S4]]가 걸렀어야 하는 경우다. 항목을 더하지 않고 처리 이력에만 적는다. 로그에 남긴다.
- **2b. 파일 쓰기가 실패한다** (디스크 오류 등)
  - 2b1. 예상하지 못한 오류로 배치가 멈춘다([[#UC-A1]] \*a). 목록 파일과 처리 이력은 반영된 데까지 남고, 마무리 단계가 그것을 올린다.
- **4a. 목록에 쓰지 않는 모드다**
  - 4a1. 더하지도 적지도 않는다. 무엇이 들어갔을지는 로그에만 남긴다([[#UC-A1]] 1b).

기록은 두 곳에 남는다. **로그**는 사람이 읽는 상세이고, 저장소의 **실행 요약**은 실행마다 견줄 값만 담은 한 줄이다. 로그는 보관 기간이 지나면 사라지고 과거와 견주려면 실행을 하나씩 열어야 하는데, 실행 요약이 그 비교를 대신한다([[CCR-RFQ-001#Q15]]).

| 실행 요약 한 줄에 담는 것 | 로그에만 남기는 것 |
|---|---|
| 실행 식별자 · 기준일 · 실행 종류(예약·수동) · 결과(성공·실패·중단) · 결과가 실패면 실패 사유의 종류(전 소스 실패 · 목록 파일 읽기 실패 · 처리 이력 읽기 실패 · 처리 이력 감소) · 올린 뒤 처리 이력에 남은 남김 기록의 수([[#UC-S4]] 2c) | 소스별 원문 실패 사유 |
| 소스별 수집 건수와 정규화 뒤 건수 · 실패 표시와 실패의 종류(연결·응답 코드·형식·수집 금지·설정 누락) | 적재한 대회의 이름과 출처 |
| 단계별 탈락 건수(정규화 탈락 · 마감 지남 · 이미 아는 대회 · 버림) | 판별 모델이 버린 대회와 그 근거 |
| 적재 건수 · 판별 실패 건수 · 미룬 건수 | 정규화에서 버린 레코드의 출처와 이유 |
| 경고(소스 0건과 그 소스가 마지막으로 건수를 낸 기준일 · 판별 미룸과 원인(키 누락·호출 실패) · 요약 파일 손상) · 소요 시간 | 예외의 원문 |

실행 식별자는 실행 번호와 시도 번호를 함께 담는다(0.1). 같은 날 여러 번 돈 실행을 가르고, 마무리 단계가 "이 실행이 줄을 남겼는가"를 판단하는 데 쓴다.

**기본 흐름**

1. 소스별 수집 건수와 정규화 뒤 건수, 실패 표시·실패의 종류를 모은다.
2. **소스 0건 경고**를 판단한다. 건수는 정규화 뒤의 것으로 센다. 이번에 오류 없이 0건을 낸 소스에 대해, 실행 요약에서 그 소스의 0건이 시작되기 바로 앞까지 **연속 N일(설정값, 기본 3)** 1건 이상을 냈으면 경고를 붙인다. 연속은 실행 횟수가 아니라 기준일로 센다. 같은 기준일에 줄이 여럿이면, 하나라도 1건 이상이면 그날을 건수를 낸 날로, 모두 0건이면 0건인 날로 본다. 같은 날 다시 돌린 실행이 연속을 부풀리지 않게 하기 위해서다. 그 소스를 수집하지 않았거나 실패 표시를 받은 줄은 연속을 끊지도 잇지도 않고 건너뛴다. 0건이 이어지는 동안에는 늘 그 시작점 앞의 기록과 견주므로 매 실행 경고가 붙는다. 바로 앞 실행 한 줄과만 견주면 0건이 된 첫날의 줄이 다음 날의 기준이 되어 둘째 날부터 경고가 사라진다. 경고에는 그 소스가 마지막으로 1건 이상을 낸 기준일을 함께 적는다.
3. [[#UC-S5]] 2c의 **판별 미룸 경고**를 붙인다. 경고는 결과를 바꾸지 않는다. 며칠 늦게 봐도 되거나, 소스 0건처럼 무엇을 놓쳤는지 배치가 알 수 없는 경고까지 실패로 만들면, 실패 표시가 흔해져 정작 급한 날이 가려진다. 그날 조치가 필요한 고장 — 접수마감일이 기준일인 대회를 넣지 못한 것 — 은 목록 파일에 더하는 방식에서는 커밋 실패로만 일어나고, 그것은 줄 없이 Actions 실패로 드러난다([[#UC-A1]] 9a5 · [[CCR-RFQ-001#Q6]]).
4. 단계별 탈락 건수와 적재·실패 건수를 모은다. 결과가 실패면 실패 사유의 종류를 적는다.
5. 적재한 대회와 판별 근거를 로그에 남긴다.
6. 전체 소요 시간을 잰다.
7. 로그로 보낼 내용에서 비밀값을 가린다. 실행 요약에는 원문 문자열을 애초에 넣지 않는다. 공개 저장소라 둘 다 그대로 노출되고, 저장소 파일은 git 이력에서 지워지지 않는다.
8. 실행 요약 파일에 한 줄을 덧붙인다. 파일은 한 번에 통째로 바뀌게 쓴다. 저장소 커밋은 [[#UC-A1]] 9의 마무리 단계가 목록 파일·처리 이력과 묶어 한 번에 한다. 남김 기록의 수는 마무리 단계가 처리 이력을 얹은 뒤 세어 채운다.

**확장**

- **2a. 실행 요약에 앞선 줄이 없다**
  - 2a1. 견줄 대상이 없으므로 소스 0건 경고를 붙이지 않는다. 첫 실행이 여기 해당한다.
- **2b. 0건이 시작되기 전 연속으로 건수를 낸 날이 N일에 못 미친다**
  - 2b1. 경고를 붙이지 않는다. 원래 드문드문 건수를 내던 소스이거나, 기록이 아직 쌓이지 않았다. 대회를 직접 여는 소스는 열린 대회가 실제로 없는 시기가 있어, 한 번이라도 건수를 낸 적이 있다는 것만으로 경고하면 고칠 것이 없는 경고가 계속 붙는다.
  - 2b2. 그래서 이런 소스가 멈추면 경고로는 알 수 없다. 받아들인 한계다.
- **2c. 실행 요약 파일에 읽히지 않는 줄이 있다**
  - 2c1. 그 줄을 건너뛰고 판단한다. **요약 파일 손상 경고**를 붙인다.
- **7a. 예외 메시지에 자격증명이 들어 있다**
  - 7a1. 로그에는 가린 뒤 남긴다. 실행 요약에는 실패의 종류만 들어가므로 원문이 들어갈 자리가 없다.
- **8a. 목록에 쓰지 않는 모드다**
  - 8a1. 실행 요약에 줄을 붙이지 않는다. 로그에만 남긴다([[#UC-A1]] 1b · [[CCR-SCN-001#S6]]). 미리보기가 실제 실행의 기록과 섞이지 않게 하기 위해서다.

**기본 흐름**

1. 참가자가 대회의 상태를 넷 중 하나로 고르거나, 지우기를 누른다.
2. 페이지가 화면을 먼저 바꾸고 저장 중 표시를 보인다.
3. 읽어 둔 상태 파일 내용에 그 대회의 값(상태 · 감춤 여부 · 바꾼 시각)을 얹어 새 내용을 만든다. 다른 대회의 값은 그대로다.
4. GitHub Contents API로 상태 파일을 읽어 둔 판 위에 커밋한다. 커밋 메시지는 정해진 형식으로, 바꾼 대회와 값을 담는다([[CCR-API-001]]).
5. 응답의 새 판을 기억하고 저장 중 표시를 지운다.

**확장**

- **1a. 페이지에 토큰이 없다**
  - 1a1. 화면을 바꾸지 않고 토큰이 필요하다고 알린 뒤 [[#UC-H2]]를 연다. 토큰을 넣고 나면 1부터 다시 한다.
- **1b. 지운 대회를 되살린다**
  - 1b1. 접힌 목록을 펼쳐 되살리기를 누른다. 감춤을 푸는 것 말고는 3부터 같다.
- **4a. 판이 어긋난다** (읽어 둔 판이 최신이 아니다 — 다른 기기의 페이지가 먼저 썼다)
  - 4a1. 저장소가 쓰기를 거절한다. 페이지가 최신 상태 파일을 다시 읽고, 이번 바꿈만 그 위에 얹어 한 번 더 쓴다. 다른 기기가 바꾼 다른 대회의 값은 남는다.
  - 4a2. 그래도 거절되면 4b로 간다.
- **4b. 커밋이 실패한다** (권한 없음 · 토큰 만료 · 네트워크)
  - 4b1. 화면을 바꾸기 전 값으로 되돌리고 실패했다고 알린다. 저장소의 상태 파일은 이전 판 그대로다.
  - 4b2. 권한이나 토큰 문제면 [[#UC-H2]]로 토큰을 다시 넣는다.
- **4c. 배치가 같은 때 커밋한다**
  - 4c1. 배치는 목록 파일과 기록 파일을, 페이지는 상태 파일을 쓴다. 파일이 다르므로 부딪히지 않는다. 다만 배치의 커밋이 먼저 들어가면 페이지가 읽어 둔 판이 저장소 전체로는 낡았을 수 있는데, Contents API는 파일 단위의 판으로 견주므로 상태 파일의 판이 그대로면 그대로 들어간다.

2. 페이지가 만드는 법을 안내한다. GitHub 설정의 fine-grained 토큰에서, 저장소는 이 저장소 하나, 권한은 Contents 읽기·쓰기만, 만료 기한을 두라는 것이다.
3. 참가자가 토큰을 붙여 넣는다.
4. 페이지가 그 토큰으로 상태 파일을 읽어 본다. 읽히면 유효한 토큰으로 본다. 상태 파일이 아직 없어 없다는 답이 와도 읽힌 것으로 본다. 저장소가 공개라 fine-grained 토큰은 쓰기 권한이 없어도 읽기는 되므로, 쓰기 권한은 여기서 가르지 못한다(4b).
5. 브라우저 저장소에 둔다. 서버가 없으므로 다른 곳으로 보내지 않는다.
6. 설정을 닫는다. 이제 [[#UC-H1]]이 된다.

**확장**

- **3a. 토큰을 지운다**
  - 3a1. 브라우저 저장소에서 지운다. 페이지는 읽기만 되는 상태로 돌아간다. GitHub 쪽의 토큰은 그대로이므로 폐기는 참가자가 GitHub에서 한다.
- **4a. 읽히지 않는다** (틀린 값 · 만료 · 요청 한도)
  - 4a1. 저장하지 않고 이유를 알린다. 3으로 돌아간다.
- **4b. 쓰기 권한이 모자란 토큰이다** (Contents 읽기만 준 토큰 · 이 저장소를 고르지 않은 토큰)
  - 4b1. 4를 지나 저장된다. 첫 저장에서 저장소가 쓰기를 거절하면 [[#UC-H1]] 4b대로 값을 되돌리고 알린다. 참가자가 Contents 읽기·쓰기 권한이 있는 토큰으로 3부터 다시 한다.
- **5a. 토큰이 샌 것 같다**
  - 5a1. 참가자가 GitHub에서 그 토큰을 폐기하고 새로 만들어 3부터 한다. 권한이 이 저장소의 파일에 그치므로, 새더라도 저장소 이력에서 무엇이 바뀌었는지 보고 되돌릴 수 있다([[CCR-RFQ-001#Q7]]).
- **5b. 브라우저 저장소를 지웠거나 다른 브라우저다**
  - 5b1. 토큰이 없으므로 [[#UC-A2]] 4b가 된다. 다시 넣는다.
