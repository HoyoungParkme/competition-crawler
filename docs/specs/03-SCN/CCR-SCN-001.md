# 사용자 시나리오

## 0. 범위와 전제

배치 한 번이 도는 동안 무엇이 벌어지는지, 그리고 사람이 그 결과를 어떻게 쓰는지를 적는다. 사람이 마주하는 곳은 이 프로젝트의 **대회 목록 페이지** 한 곳이다. 배치가 저장소의 목록 파일에 더한 대회를 페이지가 보여 주고, 사람은 페이지에서 상태를 바꾸고 관심 없는 대회를 지운다. 2026-09-29까지는 노션 `대회목록` DB가 그 자리였다.

전제는 아래와 같다.

| 전제 | 근거 |
|---|---|
| 배치는 하루 한 번 08:50 KST에 시작하도록 예약돼 있다. 예약 실행이라 조금 밀릴 수 있다 | [[CCR-PRD-001#R7]] |
| 실행은 한 번에 하나씩 차례로 돈다. 목록에 쓰는 실행은 기본 브랜치에서만 돈다 | [[CCR-PRD-001#R7]] · [[CCR-PRD-001#N5]] |
| 한 실행은 시작한 시각의 KST 날짜 하나를 **기준일**로 삼아 끝까지 쓴다 | [[CCR-PRD-001#R3]] |
| 사람에게 가는 알림은 없다. 다만 그날 조치가 필요한 고장은 실행을 실패로 남겨 Actions에 드러낸다 | [[CCR-PRD-001]] 2장 비목표 · [[CCR-PRD-001#R8]] |
| 마감 판정 기준은 접수마감일이다. 마감일이 기준일인 대회는 남는다 | [[CCR-PRD-001#R2]] · [[CCR-PRD-001#R3]] |
| 배치가 넣는 곳은 저장소의 **목록 파일**이고, 페이지가 쓰는 곳은 **상태 파일**이다. 목록 파일은 배치만, 상태 파일은 페이지만 쓴다 | [[CCR-PRD-001#R6]] · [[CCR-PRD-001#R10]] |
| `상태`와 지우기는 사람만 페이지에서 바꾼다. 배치는 목록 파일에 더하기만 하고 이미 있는 항목을 고치거나 지우지 않는다 | [[CCR-PRD-001#R6]] · [[CCR-PRD-001#R10]] |
| 페이지는 GitHub Pages의 정적 페이지다. 상태 파일을 쓰려면 사용자가 브라우저에 둔 GitHub 토큰이 필요하다 | [[CCR-PRD-001#R10]] · [[CCR-PRD-001#N3]] |
| 배치는 한 번 판별한 대회를 남긴 것이든 버린 것이든 기록해 두고 다시 묻지 않는다. 이 기록을 **처리 이력**이라 부른다 | [[CCR-PRD-001#R4]] · [[CCR-PRD-001#R5]] |
| 배치는 실행마다 저장소의 **실행 요약** 파일에 한 줄을 남긴다. 결과는 성공·실패·중단 셋 중 하나다. 미리보기 실행, 앞 실행을 기다리다 취소된 실행, 커밋이 끝내 실패한 실행, 실행 환경이 통째로 멈춰 마무리 단계까지 돌지 못한 실행만 줄이 없다 | [[CCR-PRD-001#R8]] |

시나리오에 나오는 대회 이름과 수치는 실제 소스에서 확인한 값이다. event-us에서 접수마감이 남은 대회는 2026-09-16 기준 56건이었다. 소스의 내용은 매일 바뀌므로 이 숫자는 그날의 스냅샷이다.

## 1. 페르소나

#### P1 대회를 찾아 참가하는 사람

AI·개발 분야 대회에 꾸준히 참가한다. 지금까지는 사이트를 직접 열어 조건을 걸고 눈으로 훑은 뒤 참가할 만한 것을 노션에 손으로 옮겨 적었다.

겪는 문제는 둘이다. 찾는 일이 매번 반복되고, 며칠 안 보면 마감이 지난 뒤에 대회의 존재를 알게 된다. 원하는 것은 "무엇에 참가할지" 고르는 판단만 남기는 것이다.

하루 중 페이지를 여는 시간은 아침이다. 마감일 순으로 정렬된 목록을 훑고, 참가하기로 한 것의 `상태`를 바꾸고, 관심 없는 것은 지운다.

#### P2 도구를 고치는 사람

P1과 같은 사람이지만 역할이 다르다. 배치가 깨졌거나 엉뚱한 것이 들어왔을 때 원인을 찾아 고친다.

겪는 문제는 알림이 없다는 것이다. 페이지에 아무것도 안 늘어난 날이 "새 대회가 없던 날"인지 "배치가 죽은 날"인지 구분이 안 된다. 원하는 것은 실행 기록만 보면 어느 쪽인지 바로 아는 것이다.

## 2. 시나리오

#### S1 평소 아침, 새 대회가 페이지에 들어와 있다

**주체**: [[#P1]]
**상황**: 평일 아침 9시 무렵. 배치는 08:50에 시작해 이미 끝났다.

1. 08:50 KST에 배치가 깨어난다. 기본 브랜치의 최신 커밋을 받고, 시작 시각을 KST로 바꿔 기준일을 정한다.
2. 여섯 소스에서 대회 목록을 가져온다. event-us는 분야로 좁히지 않고 행사유형이 `대회/공모전`인 것을 전부 가져오되, 접수 중이거나 접수마감일을 모르는 공고만 받는다. wevity와 콘테스트코리아는 목록이 커서 [[#P1]]이 고른 분야만 받는다. wevity는 다섯 분야, 콘테스트코리아는 두 분야다.
3. 소스마다 다른 필드를 하나의 형식으로 맞춘다. 날짜는 KST로 바꿔 날짜만 취한다. 대회명·상세링크·출처·원천 ID를 못 채운 레코드는 여기서 버려지고 건수가 기록에 남는다.
4. 접수마감일이 기준일보다 이른 대회를 버린다. 마감일이 기준일인 대회는 남긴다.
5. 이미 아는 대회를 뺀다. 목록 파일과 처리 이력을 함께 본다. LLM 판별보다 먼저 해서 같은 대회를 두 번 묻지 않는다.
6. 처음 보는 대회만 LLM에 물어 관심 분야인지 가른다. **버린 대회는 이때 곧바로 처리 이력에 적는다.**
7. 남긴 대회를 목록 파일에 더한다. `출처`·`수집일`·판별 근거도 채운다. 상태는 넣지 않는다. 상태 파일에 값이 없는 대회를 페이지가 `시작 전`으로 보여 준다. **판별을 마친 대회는 곧바로 목록 파일과 처리 이력에 적는다.**
8. 마무리 단계가 목록 파일·처리 이력·실행 요약을 한 커밋으로 올린다. 실행 요약에는 이 실행의 한 줄이 붙는다. 실행 식별자·기준일·결과·건수·경고가 담긴다. 커밋이 끝내 실패하면 셋 다 올라가지 않고, 다음 실행이 같은 대회를 다시 판별한다.
9. [[#P1]]이 아침에 페이지를 연다. 목록은 마감일 순이라 어제 없던 대회가 제자리에 끼어 있다.
10. 마감일과 대회명을 보고 참가할 것을 골라 `상태`를 `진행 중`으로 바꾼다([[#S8]]).

**변형 — 새로 들어올 대회가 없는 날**: 7에서 넣을 것이 없다. 목록 파일은 그대로이고 실행은 성공으로 끝난다. [[#P2]]가 "새 대회가 없던 날"로 보려면 실행 요약의 마지막 줄이 **오늘 날짜이고, 결과가 성공이며, 소스 실패 표시도 경고도 없이 적재가 0건**이어야 한다. 넷 중 하나라도 어긋나면 고장이다.

**변형 — 예약 실행이 밀린 날**: GitHub의 예약 실행은 요청이 몰리면 늦게 시작한다. 그래서 [[#P1]]이 9에서 페이지를 열었을 때 아직 오늘 들어온 대회가 없을 수 있다. 배치가 죽은 것이 아니라 아직 안 끝난 것이다. 조금 뒤 다시 열면 들어와 있다. 늦게 돌아도 결과는 제시간에 돈 것과 같다.

**변형 — 오늘 줄이 없다**: 며칠째 페이지에 새 대회가 없다. [[#P1]]은 [[#P2]]로서 실행 요약 파일을 여는데 마지막 줄의 날짜가 오늘이 아니다. 요약만으로는 원인을 가를 수 없다. 아직 도는 중일 수도, 커밋이 실패했을 수도, 아예 돌지 않았을 수도 있다. 그래서 **Actions 실행 이력을 함께 본다.**

| Actions 이력 | 뜻 | 할 일 |
|---|---|---|
| 오늘 실행이 돌고 있다 | 밀린 것뿐이다 | 끝날 때까지 기다린다 |
| 오늘 목록에 쓰는 실행이 끝났는데 줄이 없다 | 저장소 커밋이 실패했거나, 강제 취소나 실행 환경 유실로 마무리 단계가 돌지 못했다 | 로그를 보고 고친 뒤 다시 돌린다 |
| 오늘 미리보기 실행이나, 기다리다 취소된 실행만 있다 | 둘 다 원래 줄을 남기지 않는다 | 아래 줄과 같이 본다 |
| 오늘 실행이 아예 없다 | 워크플로가 꺼졌거나 예약이 건너뛰어졌다 | 워크플로가 켜져 있는지 보고, 꺼져 있으면 켠 뒤 새로 수동 실행한다 |

GitHub는 공개 저장소에 한동안 활동이 없으면 예약 워크플로를 끄고, 요청이 크게 몰리면 예약 실행을 건너뛰기도 한다.

**변형 — 오늘 마감인 대회를 넣지 못했다**: 목록 파일에 더하는 데는 항목 하나만 따로 실패하는 일이 없다. 넣지 못하는 경우는 8의 커밋이 끝내 실패한 경우이고, 그때는 줄 없이 **Actions에 실패로 남는다.** 그중에 접수마감일이 기준일인 대회가 있으면 다음 날이면 4에서 마감이 지나 버려지므로 그날 안에 살려야 한다. [[#P2]]가 GitHub 실패 알림을 켜 뒀다면 메일로도 받는다. [[#P2]]는 그날 안에 원인을 고쳐 다시 돌린다.

**변형 — 접수마감일을 알 수 없는 대회**: 4에서 버리지 않고 남긴다. 놓치는 쪽이 잘못 넣는 쪽보다 나쁘다.

**성공 조건**: [[#P1]]이 어느 사이트도 열지 않고, 그날 새로 뜬 관심 분야 대회를 페이지에서 전부 본다. 페이지에 새 대회가 없는 날, 그것이 "대회가 없던 날"인지 "배치가 안 돈 날"인지 실행 요약과 Actions 실행 이력만 보고 가를 수 있다.
**연관 요구사항**: [[CCR-PRD-001#R1]] · [[CCR-PRD-001#R2]] · [[CCR-PRD-001#R3]] · [[CCR-PRD-001#R4]] · [[CCR-PRD-001#R5]] · [[CCR-PRD-001#R6]] · [[CCR-PRD-001#R7]] · [[CCR-PRD-001#R8]] · [[CCR-PRD-001#R10]] · [[CCR-PRD-001#N5]]

#### S2 처음 돌리는 날, 빈 목록에 한꺼번에 들어온다

**주체**: [[#P1]]
**상황**: 목록 파일도 처리 이력도 아직 없다. 노션에 손으로 적어 둔 대회 10건은 옮기지 않는다. 배치를 처음 돌린다.

1. 배치가 목록 파일과 처리 이력이 없는 것을 빈 것으로 보고 시작한다. 파일이 있는데 읽히지 않는 것과는 다르다([[#S6]]).
2. 수집·정규화·마감 필터를 거쳐 후보가 남는다. 아는 대회가 없으므로 전부 처음 보는 대회다.
3. 후보끼리 같은 대회를 묶는다([[#S3]]). 판정은 연도·회차, 접수 기간, 정규화한 대회명 차례로 본다. 정규화는 `모집`·`공고`·`안내` 같은 꼬리말, 대괄호 머리말, `(~9/20)` 같은 괄호 날짜를 떼고, `2026년`을 `2026`으로 맞추고, 공백과 기호를 없애는 것이다.
4. 묶음의 대표를 전부 LLM에 묻는다. 여섯 소스를 합치면 수백 건이라 이날만 호출이 몰린다.
5. 남긴 대회가 한꺼번에 목록 파일에 들어간다. 나누지 않고 전부 넣는다. 접수마감 전인 것만 남으므로 물량이 무한정 늘지 않고, 나눠 넣으면 첫날 이후 며칠간 목록이 반쪽이라 [[#P1]]이 무엇을 본 건지 알 수 없게 된다.
6. [[#P1]]이 페이지를 열면 수백 건이 마감일 순으로 있다. 노션에 적어 뒀던 대회도 소스에 있는 것은 여기 다시 나타난다. 상태는 모두 `시작 전`이다. 참가 중인 것은 상태를 바꾸고, 관심 없는 것은 지운다([[#S8]]). 다음 날부터는 처리 이력에 없는 새 대회만 묻고 넣는다.

**변형 — 이듬해 같은 이름의 대회가 열린다**: 처리 이력에는 작년 대회가 남아 있다. `2026 한국관광 데이터랩 활용 경진대회`는 `2025 한국관광 데이터랩 활용 경진대회`와 제목이 0.94로 비슷하지만 **연도가 달라 다른 대회로 본다.** 이름에 연도가 없으면 접수 기간으로 가른다. 올해 접수가 작년 마감 뒤에 시작하면 다른 대회다. 연도도 날짜도 없어 가를 수 없는 경우는 예전 기록 때문에 빠진다(4장).

**변형 — 제목이 정규화로도 안 맞는다**: 연도·회차가 어긋나지 않고 접수 기간으로도 갈리지 않으면서 유사도가 0.90 이상이면 같은 대회로 본다. `2026 데이터·AI 혁신 챌린지 통합경진대회`와 event-us의 `2026 데이터·AI 혁신 챌린지 통합경진대회 데이터 문제해결 부문 모집`은 0.82라 여기 걸리지 않는다. 같은 대회지만 판단하지 않으므로, 둘 다 판별에서 남으면 항목이 둘 생기고 [[#P1]]이 보고 하나를 지운다. 문턱을 낮추면 이름 틀이 비슷한 다른 대회까지 같은 대회로 묶여 놓친다([[CCR-PRD-001]] 5.2).

**성공 조건**: 첫날 마감 전인 관심 분야 대회가 전부 목록에 들어오고, 다음 날부터는 처리 이력에 없는 새 대회만 판별된다. 해가 다른 대회가 같은 대회로 묶이지 않는다. 이름을 크게 다르게 쓴 공고는 위 변형처럼 따로 들어올 수 있다.
**연관 요구사항**: [[CCR-PRD-001#R4]] · [[CCR-PRD-001#R5]] · [[CCR-PRD-001#R6]] · [[CCR-PRD-001#R9]] · [[CCR-PRD-001#R10]] · [[CCR-PRD-001#N1]]

#### S3 같은 대회가 여러 갈래로 들어온다

**주체**: 배치
**상황**: event-us에 같은 대회가 세 번 등록되어 있고, 같은 대회가 다른 소스에도 있다.

1. event-us에서 `2026년 Big Data 활용 대회 참가자 모집`, `2026 Big Data 활용대회 참가자 모집`, `2026 Big Data 활용 대회 참가자 모집` 세 건이 들어온다. 소스 쪽에 실제로 중복 등록된 건이다.
2. 정규화하면 셋이 같은 문자열이 된다.
3. 셋을 한 묶음으로 본다. 묶을 때는 **묶음 안의 모든 짝이 같다고 나와야** 한다. 연도·회차나 접수 기간으로 다르다고 나온 짝은 물론, 유사도가 문턱에 못 미쳐 판단하지 않은 짝이 하나라도 있어도 묶지 않는다. 이 조건이 없으면 연도 없는 공고 하나를 사이에 두고 서로 다른 해의 두 공고가 한 묶음이 되고, 이름 틀이 비슷한 서로 다른 공모전이 사슬로 이어진다. 2026-09-27 자료로는 주최만 다른 아이디어 공모전 스무 건이 한 묶음이 될 뻔했다.
4. 묶음에서 목록에 넣을 대표를 정한다. 접수 시작일·마감일이 더 채워진 쪽을 대표로 삼는다.
5. 그것도 같으면 소스 우선순위를 따른다. DACON · Kaggle · AI팩토리가 앞서고, 그다음이 event-us, 마지막이 wevity · 콘테스트코리아다. 앞쪽은 대회를 직접 여는 플랫폼이라 링크가 곧 참가 페이지이고, 뒤쪽은 공모전 포털이라 원본으로 한 번 더 타고 들어가야 할 수 있다.
6. 목록 파일에는 항목이 하나만 생긴다. `출처`에는 대표의 소스가 들어간다. 처리 이력에는 대표뿐 아니라 묶음의 나머지 구성원도 같은 결과로 적힌다. 그래야 다음 날 구성원 쪽이 따로 들어오지 않는다.

**변형 — AI팩토리가 대회를 과제로 쪼개 올린다**: `2026 국립공원 위성 모니터링 AI 챌린지`는 AI팩토리에 과제 4건(`주제 1: 구상나무 고사 탐지 및 분포 분석` 등)으로 올라와 있고 접수마감일도 과제마다 다르다. 과제명은 서로 달라 위 판정으로는 묶이지 않으므로, 정규화 단계에서 같은 대회에 속한 과제를 레코드 하나로 합친다. 대회명은 대회 이름을, 접수마감일은 가장 늦은 과제의 날짜(10/6)를 쓴다. 그래서 event-us의 같은 대회 공고와도 한 묶음이 되고 목록에는 항목이 하나만 생긴다.

**변형 — 제목이 많이 다르다**: 유사도가 0.90에 못 미치면 같다고 보지 않는다. 항목이 둘 생기고 [[#P1]]이 보고 하나를 지운다. 놓치는 것보다 낫다고 본 결과다. 2026-09-27 자료에서는 같은 대회인데 0.90에 못 미친 짝이 10개 있었다. `총상금 2,750만원｜…`처럼 앞에 말을 붙였거나, 짧은 이름에 연도만 더 붙은 경우다.

**성공 조건**: 같은 대회에 대해 목록 항목이 하나만 남는다. 이름을 크게 다르게 쓴 공고는 위 변형의 예외다. 다른 대회가 잘못 묶이지 않는다. 2026-09-27 자료의 접수 중 후보 321건을 묶었을 때 구성원이 여럿인 묶음 59개 가운데 57개가 실제로 같은 대회였다. 2026-09-16 자료(문턱 0.80 때)의 접수마감 전 56건을 전수 대조했을 때 묶인 4쌍은 모두 실제로 같은 대회였고, 지난 대회 2,089건과 견줬을 때 잘못 묶인 건은 없었다.
**연관 요구사항**: [[CCR-PRD-001#R2]] · [[CCR-PRD-001#R5]]

#### S4 관심 없는 대회가 섞여 들어온다

**주체**: 배치
**상황**: 분야로 좁히지 않으므로 창업 경진대회·사진 공모전·영상제·교육과정 모집이 함께 들어온다.

1. 마감 전 후보 중 창업 경진대회가 큰 몫을 차지한다. 2026-09-16 기준 56건 중 14건이었다.
2. 이미 아는 대회를 뺀 뒤 처음 보는 대회만 LLM에 한 건씩 묻는다.
3. 판별 결과와 그 근거가 Actions 로그에 남는다.
4. 관심 분야로 판정된 것만 목록에 들어간다.
5. 버린 대회도 처리 이력에 적힌다. 다음 날 같은 창업 경진대회가 또 수집되지만 처리 이력에 있으므로 다시 묻지 않는다. 이것이 없으면 마감 전까지 매일 같은 대회를 되물어 비용이 여러 배가 된다.
6. [[#P2]]가 나중에 기록을 보고 잘못 버린 건이 있으면 판별 기준을 고친다.

**변형 — 판별이 몇 건만 실패한다**: 그날 판별 대상 중 실패가 절반 이하다. 실패한 대회는 버리지 않고 목록에 넣는다. [[#P1]]이 보고 관심 없으면 지우면 된다. 판별이 안 됐다고 대회를 잃지는 않는다.

**변형 — 판별이 통째로 실패한다**: API 키가 만료됐거나 크레딧이 떨어져 그날 판별 대상 중 절반을 넘게 실패한다. 이때 위와 같이 전부 넣으면 창업·사진 공모전까지 목록에 쏟아지는데 실행은 성공으로 끝나 [[#P1]]은 이유를 모른다. 그래서 판별하지 못한 대회는 **그날 넣지 않고 처리 이력에도 적지 않는다.** 다만 **접수마감일이 기준일인 대회는 미루면 잃으므로 넣는다.** 비관심 대회가 몇 건 섞일 수 있지만 그런 대회는 수가 적다. 실행 요약에 경고가 붙고 결과는 성공이다. 다음 날 배치는 미룬 대회들을 처음 보는 대회로 여기고 다시 판별한다. [[#P2]]는 경고를 보고 키를 고친다. 대회는 하루 늦게 들어온다.

**변형 — 관심 없는 대회가 잘못 남는다**: [[#P1]]이 페이지에서 그 대회를 지운다([[#S8]]). 지우기는 목록 파일의 항목을 없애는 것이 아니라 상태 파일에 감춤으로 적는 것이라, 배치가 보는 목록 파일에는 그 대회가 그대로 있다. 처리 이력에도 남김으로 적혀 있다. 그래서 다음 실행에서 다시 들어오지 않는다.

**변형 — 판별 기준을 고친다**: [[#P2]]가 "AI 주제 아이디어 공모전은 남긴다"로 기준을 넓힌다. 그런데 어제까지 이 기준으로 버린 대회는 처리 이력에 "버림"으로 남아 있어 다시 묻지 않는다. 순서는 이렇다.

1. 기본 브랜치가 아닌 곳에 새 기준을 올리고, 목록에 쓰지 않는 모드로 돌린다. 이때 **버린 기록을 없는 것으로 보고** 판별하게 해서, 기록을 비웠을 때 무엇이 들어올지까지 본다. 목록 파일도 처리 이력도 실행 요약도 바뀌지 않는다.
2. 결과가 괜찮으면 **기준 변경과 버림 기록 비우기를 한 커밋으로** 기본 브랜치에 넣는다. 비우기는 브랜치에 있는 처리 이력 사본이 아니라 넣기 직전의 기본 브랜치 최신 처리 이력에서 한다. 브랜치를 딴 뒤 매일 실행이 새로 적은 버림은 사본에 없다. 둘을 따로 넣으면, 기록만 먼저 비웠을 때 그 사이에 돈 실행이 옛 기준으로 다시 버려 비우기가 무효가 된다.
3. 다음 실행에서 마감 전인 버린 대회가 새 기준으로 다시 판별되고, 새로 관심 분야가 된 것만 목록에 들어간다. 남긴 기록은 그대로라 이미 목록에 있는 대회가 두 번 들어가지 않는다.

**성공 조건**: 새로 적재된 건 중 [[#P1]]이 관심 없다고 판단해 지우는 비율이 20% 이하다. 한 번 지운 대회가 다시 들어오지 않는다. 한 번 판별한 대회를 다시 묻지 않는다. 판별이 통째로 실패한 날 비관심 대회가 쏟아지지 않고, 그날 마감인 대회도 잃지 않는다.
**연관 요구사항**: [[CCR-PRD-001#R4]] · [[CCR-PRD-001#R5]] · [[CCR-PRD-001#R8]] · [[CCR-PRD-001#N1]]

#### S5 소스 하나가 깨진 날

**주체**: [[#P2]]
**상황**: wevity가 마크업을 바꿔 목록 파싱이 실패한다.

1. 배치가 여섯 소스를 돈다. wevity에서 예외가 난다.
2. 그 소스만 빈 결과로 두고 나머지 다섯 소스의 결과로 계속 진행한다.
3. 목록에는 다섯 소스에서 온 대회가 평소처럼 들어간다.
4. 실행 요약에 `wevity 실패`와 실패의 종류가 남고, 원문 사유는 Actions 로그에 남는다. 실행 자체는 성공으로 끝난다.
5. [[#P2]]가 기록을 보고 파서를 고친다.

**변형 — 여섯 소스가 전부 실패한다**: 실행을 실패로 끝낸다. 네트워크나 설정이 통째로 잘못된 경우라 조용히 넘어가면 안 된다. 실패로 끝나도 실행 요약에 한 줄은 남는다.

**변형 — 그 소스의 설정만 빠졌다**: Kaggle API 토큰이 없으면 Kaggle만 실패로 다루고 나머지 다섯 소스는 평소대로 적재된다. 목록 파일과 처리 이력이 없는 첫 실행은 빈 것으로 보고 돈다([[#S2]]). 있는데 읽히지 않으면 이미 아는 대회를 가를 수 없으므로 수집을 시작하지 않고 실행이 실패로 끝난다([[#S6]]).

**변형 — 소스 하나가 아주 느리다**: 예외도 0건도 아니고, 응답이 한참 늦거나 기다리라는 답만 온다. 그대로 기다리면 수집이 끝나지 않아 나머지 다섯 소스의 대회까지 적재되지 못한다. 그래서 소스마다 쓸 수 있는 시간에 상한을 둔다. 상한에 닿으면 그 소스만 실패로 표시하고 나머지로 진행한다. 그다음은 2~4와 같다.

**변형 — 소스는 살아 있는데 0건을 준다**: 예외가 안 나므로 4의 실패로는 잡히지 않고, 페이지만 보면 "새 대회가 없던 날"과 같아 보인다. 이것을 사람 눈에 맡기지 않는다. 배치가 실행마다 소스별 건수를 실행 요약에 쌓아 두고, **꾸준히 건수를 내던 소스가 0건을 내기 시작하면 0건이 이어지는 동안 매 실행 경고를 붙인다.** "꾸준히"는 0건이 시작되기 바로 앞까지 연속 며칠 건수를 냈는지로 가르며 그 날수는 설정값이다. 같은 날 여러 번 돌린 실행은 하루로 센다. 경고에는 그 소스가 마지막으로 건수를 낸 날짜가 함께 적혀, [[#P2]]가 언제부터인지 안다. 바로 앞 실행 하나와만 견주면 0건이 된 첫날의 줄이 다음 날의 기준이 되어 둘째 날부터 경고가 사라진다. 건수는 정규화를 거친 뒤의 것으로 센다. 파서가 레코드를 내면서 대회명이나 링크를 못 채우면 전부 버려지는데, 수집 건수만 세면 그것이 드러나지 않는다. 원래 드문드문 건수를 내던 소스에는 경고를 붙이지 않는다.

**변형 — 경고를 봤는데 고칠 것이 없다**: 그 소스에 정말로 열린 대회가 없는 시기일 수 있다. 건수만으로는 파서 고장과 구별되지 않으므로 [[#P2]]가 사이트를 직접 열어 본다. 대회가 없으면 고칠 것이 없고, 그 소스가 다시 대회를 낼 때까지 경고가 붙는다.

**성공 조건**: 소스 하나가 깨져도 그날 나머지 대회가 목록에 들어간다. 예외로 깨졌든 조용히 0건이 됐든 기록만 보면 알 수 있다.
**연관 요구사항**: [[CCR-PRD-001#R8]] · [[CCR-PRD-001#R9]]

#### S6 실패한 날 다시 돌린다

**주체**: [[#P2]]
**상황**: 판별을 절반쯤 하다가 끊겼다.

1. [[#P2]]가 저장소에서 배치를 손으로 **새로** 실행한다. 끊긴 옛 실행을 그대로 다시 실행하지 않는다. 다시 실행하면 처음 실행된 때의 워크플로 정의로 돌아, 그사이 워크플로 파일을 고쳤다면 반영되지 않는다. 그런 실행은 시작하자마자 중단으로 끝난다.
2. 수집과 정규화가 처음부터 다시 돈다.
3. 앞 실행이 끊기기 전까지 판별한 대회는 마무리 단계가 올린 목록 파일과 처리 이력에 있으므로 이미 아는 대회로 빠진다.
4. 못 넣은 나머지만 들어간다.
5. 같은 날 세 번을 돌려도 결과는 한 번 돌린 것과 같다.

**변형 — 잡이 시간 초과로 강제로 끊겼다**: 배치가 스스로 끝내지 못하고 도중에 멈췄다. 판별을 마친 대회마다 목록 파일과 처리 이력에 바로 적어 두고 마무리 단계가 그것을 올리므로, 그때까지 넣은 대회는 남아 있다. 실행 요약에는 결과 **중단**으로 한 줄이 남고 Actions에도 실패로 보여, [[#P2]]가 무슨 일이 있었는지 안다. [[#P2]]가 직접 취소한 실행도 중단으로 한 줄이 남지만, Actions에는 취소로 보인다. 강제 취소나 실행 환경 유실로 마무리 단계까지 멈추면 이 줄도 남지 않는다. 그때는 [[#S1]]의 표대로 Actions 실행 이력으로 가른다. 다시 돌리면 거기서부터 이어서 채워진다. 접수마감일이 기준일인 대회가 아직 못 들어갔을 수 있으므로 그날 안에 다시 돌린다.

**변형 — 앞 실행이 아직 돌고 있다**: 뒤 실행은 취소되지 않고 기다렸다가 앞 실행이 끝난 뒤에 시작한다. 시작할 때 저장소의 최신 상태를 받으므로 앞 실행이 올린 처리 이력을 본다. 두 실행이 겹쳐 돌면 같은 대회를 둘 다 넣게 된다.

**변형 — 목록에 쓰지 않고 확인만 한다**: 적재 없이 무엇이 들어갈지만 로그로 본다. 판별 기준을 고친 뒤 영향을 미리 보는 데 쓴다([[#S4]]). 이 실행은 목록 파일도 처리 이력도 실행 요약도 바꾸지 않는다. 판별 기준을 미리 볼 때는 기본 브랜치가 아닌 곳에서 돌리고, 기본 브랜치에서도 [[#P2]]가 고르면 이 모드로 돈다. 기본 브랜치가 아닌 곳에서 도는 실행과 개발자 PC에서 돌리는 실행은 늘 이 모드다.

**변형 — 처리 이력 파일이 읽히지 않는다**: 배치는 빈 이력으로 보지 않는다. 빈 것으로 보면 버린 대회를 모두 다시 묻고, 같은 묶음으로만 기록된 공고가 새 항목으로 들어온다. 판별도 적재도 하지 않고 실행을 실패로 끝낸다. 목록 파일이 읽히지 않을 때도 같다. 빈 것으로 보면 목록 전체가 다시 들어온다. [[#P2]]는 손으로 고치다 형식을 깬 것이면 형식만 고친다. 버림 기록을 비운 커밋을 통째로 되돌리면 비우기가 무효가 되기 때문이다([[#S4]]). 그 밖의 손상이면 처리 이력과 실행 요약을 마지막으로 읽히던 판으로 함께 되돌린 뒤 다시 돌린다. 되돌리면 그 뒤에 적힌 기록이 사라진다. 처리 이력만 되돌리면 아래 변형에 걸린다.

**변형 — 처리 이력의 남김 기록이 줄었다**: [[#P2]]가 처리 이력을 손으로 고치다 남김 줄까지 지웠거나, 명령을 잘못 써 파일을 비웠다. 파일은 읽히므로 위 변형에 걸리지 않는다. 그대로 두면 버린 대회를 모두 다시 묻고 같은 묶음으로만 기록된 공고가 다시 들어온다. 그래서 배치는 실행 요약 한 줄마다 그때 처리 이력에 남은 남김 기록의 수를 적어 두고, 시작할 때 그 수가 줄었으면 판별도 적재도 하지 않고 실행을 실패로 끝낸다. 남김 기록은 판별 기준을 바꿀 때도 비우지 않으므로([[#S4]]) 정상적인 손질로는 줄지 않는다. [[#P2]]는 저장소 이력에서 지워진 줄을 되살린다. 일부러 예전 판으로 되돌린 것이면 실행 요약도 같은 판으로 함께 되돌린다. 처리 이력과 실행 요약이 함께 사라지면 견줄 값이 없어 첫 실행처럼 돈다(4장).

**성공 조건**: 몇 번을 돌려도 목록 파일이 한 번 돌린 것과 같다. 시간 한도나 취소로 끊겨도 넣은 데까지는 기록에 남고, 그 실행도 요약에 한 줄을 남긴다. 처리 이력이 줄어든 채로는 판별도 적재도 하지 않는다.
**연관 요구사항**: [[CCR-PRD-001#R5]] · [[CCR-PRD-001#R7]] · [[CCR-PRD-001#R8]] · [[CCR-PRD-001#N5]]

#### S7 목록에 있는 대회의 마감이 지난다

**주체**: [[#P1]]
**상황**: 지난주에 들어온 대회의 접수마감일이 어제였다.

1. 배치가 돌면서 그 대회를 다시 수집한다.
2. 접수마감일이 지났으므로 후보에서 버린다.
3. 이미 목록 파일에 있는 항목은 건드리지 않는다. 접수마감일도 그대로다.
4. 페이지는 마감이 지난 대회를 기본으로 접어 보여 준다. [[#P1]]은 펼쳐서 보고, 필요 없으면 지운다([[#S8]]).

**변형 — 마감일이 연장된다**: 소스에서는 마감일이 바뀌지만 목록의 기존 항목은 갱신되지 않는다. 페이지에는 예전 마감일이 그대로 보이고, 지나면 접힌다. [[#P1]]이 상세 링크를 열어야 안다. 갱신을 허용하면 어디까지가 배치의 영역인지 흐려진다. 그래서 감수하기로 한 것이며 4장에 적었다.

**변형 — 접수 기간이 통째로 미뤄진다**: 주최 측이 접수를 예전 마감일 뒤로 미뤘다. 소스의 공고가 그대로 남아 날짜만 바뀌면, 배치는 예전에 처리한 공고와 같은 공고임을 알아 새 대회로 보지 않는다. 목록의 기존 항목은 이때도 갱신되지 않는다. 다만 예전 공고가 내려가고 다른 소스에만 새 날짜로 올라오면, 날짜만으로는 새 회차와 가를 수 없어 항목이 하나 더 생긴다. [[#P1]]이 보고 지운다.

**성공 조건**: 마감이 지난 대회가 새로 적재되지 않고, 기존 항목이 배치에 의해 바뀌지 않는다. 마감이 지난 대회는 페이지에서 접힌다.
**연관 요구사항**: [[CCR-PRD-001#R3]] · [[CCR-PRD-001#R5]] · [[CCR-PRD-001#R6]] · [[CCR-PRD-001#R10]]

#### S8 페이지에서 상태를 바꾸고 지운다

**주체**: [[#P1]]
**상황**: 아침에 페이지를 열어 새로 들어온 대회를 훑는다.

1. 페이지가 기본 브랜치의 목록 파일과 상태 파일을 읽는다. 접수마감일 오름차순이고, 마감일을 모르는 대회는 맨 뒤다. 마감이 지난 대회와 지운 대회는 접혀 있다. 상태 파일에 값이 없는 대회는 `시작 전`으로 보인다.
2. [[#P1]]이 참가하기로 한 대회의 `상태`를 `진행 중`으로 바꾼다.
3. 페이지가 브라우저에 둔 토큰으로 상태 파일을 저장소에 커밋한다. 저장하는 동안 그 표시가 보이고, 끝나면 사라진다.
4. 관심 없는 대회는 지운다. 목록에서 사라지고 상태 파일에 감춤으로 적힌다. 목록 파일의 항목은 그대로다.
5. 다른 기기에서 페이지를 열어도 같은 상태와 같은 목록이 보인다. 상태가 저장소에 있기 때문이다.
6. 다음 날 배치가 돌아도 지운 대회는 다시 들어오지 않는다. 배치는 상태 파일을 쓰지 않고, 목록 파일의 항목이 그대로 있어 이미 아는 대회이기 때문이다.

**변형 — 토큰이 없다**: 처음 여는 브라우저다. 읽기는 그대로 된다. 상태를 바꾸려 하면 토큰이 필요하다고 알리고 설정을 연다. [[#P1]]이 GitHub에서 이 저장소의 파일 읽기·쓰기 권한만 있는 fine-grained 토큰을 만들어 붙여 넣는다. 토큰은 브라우저에 남아 다음부터 묻지 않는다. 저장소·페이지 주소·로그 어디에도 가지 않는다.

**변형 — 판이 어긋난다**: 다른 기기의 페이지가 먼저 상태 파일을 바꿔, 이 페이지가 읽어 둔 판이 낡았다. 저장소가 쓰기를 거절하면 페이지가 최신 상태 파일을 다시 읽고 이번 바꿈을 그 위에 얹어 다시 쓴다. 그래도 안 되면 실패했다고 알리고 바꾸기 전 값으로 되돌린다. [[#P1]]이 다시 바꾼다.

**변형 — 배치와 같은 날 커밋한다**: 배치는 목록 파일을, 페이지는 상태 파일을 쓴다. 파일이 다르므로 같은 날 각각 커밋해도 서로를 덮지 않는다.

**변형 — 지운 대회를 되살린다**: 접힌 목록을 펼치면 지운 대회가 보인다. 되살리면 감춤이 풀리고 원래 자리로 돌아온다.

**변형 — 토큰이 샌 것 같다**: [[#P1]]이 GitHub에서 그 토큰을 폐기하고 새로 만들어 페이지에 넣는다. 토큰의 권한은 이 저장소의 파일에 그치므로, 새더라도 저장소 이력에서 무엇이 바뀌었는지 볼 수 있고 되돌릴 수 있다.

**성공 조건**: 바꾼 상태와 지운 대회가 저장소에 남고, 어느 기기에서 열어도 같다. 지운 대회가 배치에서 되살아나지 않는다. 토큰이 브라우저 밖으로 나가지 않는다.
**연관 요구사항**: [[CCR-PRD-001#R5]] · [[CCR-PRD-001#R6]] · [[CCR-PRD-001#R10]] · [[CCR-PRD-001#N3]]

## 4. 받아들인 한계

시나리오를 쓰면서 드러난 문제 가운데 일부는 방법을 찾았다 — 처리 이력([[#S4]]), 소스 우선순위([[#S3]]), 실행 요약 비교([[#S5]]·[[#S1]]), 남김 기록 수 감시([[#S6]]). 나머지는 고치지 않거나 사람의 손을 빌리기로 했다. 그것과 이유를 남긴다.

| 한계 | 왜 감수하는가 |
|---|---|
| 소스에서 마감일이 연장돼도 목록의 기존 항목은 그대로다 ([[#S7]]) | 갱신을 허용하면 어디까지가 배치의 영역인지 흐려진다. `상태`를 사람만 바꾸기로 한 것과 같은 선이다. [[#P1]]은 상세 링크를 열어 확인한다 |
| AI팩토리 대회의 과제별 마감일은 목록에 보이지 않는다 ([[#S3]]) | 대회당 한 행으로 넣기로 했고 마감일은 가장 늦은 과제의 날짜다. 먼저 닫히는 과제가 있으면 [[#P1]]이 상세 링크를 열어야 안다 |
| 저장소 커밋이 실패한 실행의 결과는 하나도 남지 않아, 다음 실행이 그날의 대회를 다시 판별한다. 원인이 설정이면 고칠 때까지 매일 되풀이된다 ([[#S1]] · [[#S6]]) | 목록 파일·처리 이력·실행 요약을 한 커밋으로 올리므로 반쪽만 남는 일은 없다. Actions 실행이 실패로 남으므로 [[#P2]]가 알아챈다. 대가는 판별 호출이 한 번 더 드는 것뿐이다 |
| 판별 기준을 고쳐도 이미 버린 대회는 새 기준으로 다시 보지 않는다 ([[#S4]]) | 매일 다시 묻지 않으려고 버린 대회를 기록하기 때문이다. 기준을 바꿀 때 [[#P2]]가 버린 기록만 비우면 된다. 이 손 한 번이 매일 되묻는 비용보다 싸다 |
| 판별이 여러 날 연속 통째로 실패하면, 마감일을 아는 대회는 마감일 당일에야 판별 없이 들어오고, 마감일을 모르는 대회는 계속 미뤄지다 소스에서 내려가면 놓친다 ([[#S4]]) | 실패한 날 전부 넣으면 비관심 대회가 쏟아진다. 미룬 날마다 원인과 함께 경고가 붙으므로 [[#P2]]가 알아채고 키를 고치는 것을 전제로 한다 |
| 경고가 붙어도 Actions는 성공으로 보인다 ([[#S5]]) | 며칠 늦게 봐도 되거나, 소스 0건처럼 무엇을 놓쳤는지 배치가 알 수 없는 경고까지 실패로 만들면, 실패 표시가 흔해져 정작 급한 날이 가려진다. 그날 조치가 필요한 고장 — 오늘 마감 대회를 넣지 못한 것 — 은 커밋 실패로만 일어나고 그것은 실패로 보인다. 나머지 경고는 [[#P2]]가 실행 요약을 열어야 본다 |
| 접수마감일이 기준일인 대회를 그날 넣지 못하면 다음 날에는 마감이 지나 들어오지 못한다 ([[#S1]] · [[#S6]]) | 배치가 그 대회를 알고도 넣지 못한 날은 드러낸다. 커밋이 실패하면 Actions에 실패로, 도중에 끊기면 중단으로 남겨 실패로 보인다. [[#P2]]가 그날 안에 다시 돌리는 것을 전제로 한다. 실패하거나 조용히 0건을 낸 소스에만 있던 오늘 마감 대회는 배치가 알지 못하므로 드러나지도 않고 잃는다 ([[#S5]]) |
| 처리 이력을 실행 요약과 함께 마지막으로 읽히던 판으로 되돌리면 그 뒤에 적힌 기록이 사라진다. 그사이 같은 묶음으로만 기록된 공고는 다시 들어오고, 버린 대회는 마감 전이면 다시 판별된다 ([[#S6]]) | 빈 이력으로 보는 것보다 잃는 범위가 좁다. 읽히지 않는 동안은 판별도 적재도 하지 않아 기록이 더 쌓이지 않으므로, 사라지는 것은 마지막으로 읽히던 판과 손상된 판 사이의 기록이다 |
